一、系统概述

1.1 背景

传统 AI Coding 的四大痛点：

  • 上下文不可控 — 依赖 RAG 导致信息遗漏与幻觉
  • 长周期不稳定 — 上下文窗口膨胀，后期产出质量急剧下降
  • 无流程约束 — vibe coding 模式不可复现、不可审计
  • 无法对齐企业研发体系 — 缺乏审批、评审、质量门禁
目标：构建一个「可持续运行」的 AI 软件开发系统，覆盖从需求到复盘的全生命周期。

1.2 全流程管线

PRD→ 架构→ 设计→ 编码→ 测试→ 上线→ 复盘

1.3 六大核心原则

Principle 1
文档即状态
所有系统状态持久化为结构化文档（Git），文档是唯一真相来源
Principle 2
无 RAG
上下文由确定性的 glob 规则加载，杜绝语义检索的不确定性
Principle 3
多 Agent 协作
8 个专职 Agent，每个只做一件事，职责边界清晰
Principle 4
DAG 驱动
13 步有向无环图定义执行流程，拓扑排序保证依赖正确
Principle 5
人工审批
每步执行后暂停，等待人工 approve/reject，绝不黑盒连续执行
Principle 6
全链路可审核
每次 AI 操作的输入、输出、推理过程完整记录，可追溯

审批约束

  • 每个 DAG 步骤执行后 强制暂停，等待人工审批
  • 审批通过 → advance 进入下一步；审批拒绝 → 返工后重新提交
  • 系统设计上 不允许自动连续执行多步

可审核性要求

  • 所有 AI 产物必须记录：输入上下文、Prompt、输出产物、推理过程、关键决策
  • 每条操作独立序列化为 JSON 审计日志文件
  • 审计日志包含：操作者角色、操作类型、耗时、状态、人工审核标记

八、Agent 实现设计

核心设计变更 (v2.0)：Agent 不再自己用 Python 生成文档/代码，而是委托给 Claude Code agent。 Claude Code 以 claude -p --tools Read,Write,Edit,Bash --permission-mode auto 模式运行， 拥有完整的工具链能力，可以读上下文、写文件、跑命令。

8.1 委托模式

class PMAgent(BaseAgent):
    def run(self, input_data):
        if self.agent is None:
            raise AgentError("requires Claude Code agent")
        return self._run_agentic(...)

    def _run_agentic(self, ...):
        prompt = build_task_prompt(...)          # 中文指令
        response = self.agent.generate_agentic(  # Claude Code agent
            prompt, role="pm")
        # Claude Code 读取已有 PRD 了解格式，
        # 生成 JSON 写入 .cogniforge/wiki/prd/prd-003.json
        # wiki_renderer 随后自动渲染为 HTML
        git_stage_and_commit(output_path)

8.4 Role System Prompt & 约束系统

ROLE_PROMPTS 仅包含身份和职责（"你是 X Agent，职责: Y"）。行为约束外置为 .cogniforge/constraints/{role}.md 文件，由 ConstraintLoader 加载后注入 system prompt。文件不存在时使用内置默认值，确保系统在任何项目都能运行。

用户可编辑约束文件定制各角色行为，无需修改源码。cogniforge init 会自动生成全部默认约束文件。

设计原则说明
Agent 只做编排CogniForge Agent 构建 prompt、调用 Claude Code、git commit
Claude Code 做执行读上下文、推理、生成文件 — 真正需要 AI 的工作
无 Python fallback没有 Claude Code agent 时报错，不再用 Python 拼文档
Operational 保留pytest 运行、git 提交等纯操作逻辑保留在 Agent 中

8.5 三层接口一致性保障

多模块 LLD 生成时，模块间的接口契约必须一致。本系统通过三层防护确保接口对齐：

层位置机制作用
L1 上游约束 SAD contracts[] Architect 定义跨模块接口契约：provider、consumers、endpoint、request/response body 字段名和类型 源头约束，MDE 必须按契约实现
L2 运行时对齐 DesignAgent prompt _build_contract_context() 预组装全部上下文：① 本模块 SAD 定义 ② provider/consumer contracts ③ 从邻模块 LLD 提取已实现的接口签名 ④ 系统拓扑 ⑤ SAD tech_stack（全局技术选型约束）。prompt 自包含，LLM 无需强制读文件 执行时约束，MDE 不需要发现契约——所有约束和邻模块签名已直接注入 prompt
L3 事后校验 interface_checker.py 解析所有 SAD contracts 和 LLD JSONs，交叉比对 endpoint + response fields；design_review 自动审批前触发 下游兜底，发现冲突时拒绝审批并输出报告

L3 校验规则

检查项严重性描述
Provider LLD 缺失✗ conflictcontract 的 provider 模块没有 LLD 文档
Endpoint 缺失✗ conflictprovider LLD 未定义契约要求的接口
Response 字段缺失✗ conflictprovider LLD 的 response body 缺少契约指定的字段
Response 字段多余⚠ warningprovider LLD 的 response body 有契约未声明的字段
Consumer 未引用依赖⚠ warningconsumer LLD 未引用其依赖的 provider 接口
未声明接口⚠ warningLLD 定义的接口在 SAD contracts 中无对应声明

8.6 LLD 校验门禁 (lld_validator.py)

DesignAgent 在委托 Claude Code 生成 LLD 后，自动运行校验。校验不通过时带反馈重试（最多 2 次修正循环），确保 LLD JSON 的完整性和正确性。

校验流程

DesignAgent.run()
  ↓
Claude Code agent → 生成 LLD JSON
  ↓
lld_validator.validate_lld_json(json_path)
  ├─ 检查 meta 完整性（doc_id, type, module_type, module, title）
  ├─ 检查 overview 完整性（description 必填）
  ├─ 按 module_type 检查类型专属必填段：
  │   service:      6 段（data_models, domain_objects, service_contracts, business_rules, interfaces, error_handling）
  │   frontend:     7 段（data_models, component_tree, state_design, route_design, interaction_flows, api_integration, interfaces）
  │   gateway:      7 段（data_models, route_table, middleware_chain, auth_policy, rate_limiting, interfaces, error_handling）
  │   database:     6 段（data_models, index_strategy, migration_strategy, capacity_estimation, connection_contracts, interfaces）
  │   infrastructure: 3 段（data_models, topology, interfaces; MQ 子类型额外要求 message_contracts, reliability_strategy）
  └─ 深度字段检查（data_models ownership, domain_objects attributes, ...）
  ↓
通过？→ wiki_renderer 渲染 HTML → git commit
失败？→ 格式化反馈 → Claude Code 修正（最多 2 次重试）

校验报告

format_validation_report() 将校验失败项格式化为人类可读的反馈，直接注入修正 prompt，形成自动修正闭环。

8.7 模块类型与专属 LLD Schema

DesignAgent 从 SAD 读取模块的 module_type，按类型注入专属 JSON Schema 片段，确保每种模块类型的 LLD 包含正确的设计细节。

ModuleType专属段所有权规则
databasedata_models, index_strategy, migration_strategy, capacity_estimation, connection_contracts, interfaces拥有 canonical 数据模型定义权，其他模块只能派生引用
servicedata_models, domain_objects, service_contracts, business_rules, interfaces, error_handling数据模型标记为 owned 或 derived(source=db_module)
gatewaydata_models, route_table, middleware_chain, auth_policy, rate_limiting, interfaces, error_handling接口定义必须引用后端 service 的 contracts
frontenddata_models, component_tree, state_design, route_design, interaction_flows, api_integration, interfacesapi_integration 必须与 gateway/service 接口对齐
infrastructuredata_models, topology, interfaces（MQ 子类型额外: message_contracts, reliability_strategy）message_contracts 必须在 SAD contracts 中声明

所有权枚举值含义校验规则

8.8 Wiki 分支隔离

GitStorage.commit_to_wiki_branch() 确保 wiki 文档提交进入独立 wiki 分支，与开发分支完全隔离：

  • 创建临时 worktree → 复制文件 → 提交到 wiki 分支 → 清理 worktree
  • 开发分支的 index 中取消 wiki 文件跟踪，防止误合入主分支
  • cogniforge wiki push 命令单独推送 wiki 分支
多层防护：① .gitignore 忽略 .cogniforge/ ② git hooks 拒绝含 wiki 文件的提交 ③ wiki 产物通过 worktree 直接写入 wiki 分支 ④ index 清理确保不残留跟踪状态。

8.9 WBS 系统 — MDE→DEV 结构化翻译层 (v2.1)

WBS（Work Breakdown Structure）子系统将结构化的 LLD JSON 翻译为可追踪、可验证的 Task 单元，让 Dev Agent 无需重新阅读完整 LLD 即可直接消费任务定义。流程为机械推导 + 批处理 LLM 丰富 + 覆盖率校验。

核心模块（7 个文件）

模块文件职责
LLDArtifactRegistrywbs/lld_artifact_registry.py纯机械层 — 解析 LLD JSON，输出可枚举的 ArtifactEntry 表（data_models / domain_objects / service_contracts / interfaces 等），零 LLM
DecompositionRuleswbs/decomposition_rules.py纯机械规则引擎 — 按 module_type（5 种）分发 rule-set，输出 TaskStub（含 layer、inferred_deps、expected_output_files）
TaskStubGeneratorwbs/task_stub_generator.py整合 decompose() + 按 layer 排序（0=model → 1=service → 2=endpoint → 3=test）
AcceptanceCriteriawbs/acceptance_criteria.py按 task category 和 lld_refs 提取/生成验收标准（model→字段完整性, endpoint→请求/响应格式, test→覆盖率阈值）
TaskContextBuilderwbs/task_context_builder.py为每个 task 构建 TaskContext（含 TaskScope — data_models + domain_objects + interfaces + service_contracts + business_rules + error_handling），DEV 直接消费
CoverageValidatorwbs/coverage_validator.py验证 WBS 对 LLD 的覆盖率 — 逐 artifact 比对，报告遗漏与覆盖率，不过时触发 LLM 重试
EnrichedWBSAssemblerwbs/enriched_wbs_assembler.py总装编排器 — 串联以上 6 模块 + LLM 批处理丰富 + 覆盖率校验循环（max 2 rounds），输出 WBSResult

WBS 5 步生成流程

① LLDArtifactRegistry 解析 LLD JSON → ArtifactEntry 迭代器（机械）
      ↓
② DecompositionRules 按 module_type 分发 → TaskStub 列表（机械）
     TaskStub 包含: suggested_name, category, lld_refs, inferred_deps,
     expected_output_files, layer(0-3), confidence
      ↓
③ LLM 批处理丰富 — 为 TaskStub 补充 description, estimated_hours,
     priority, 确认/修正 deps（batch LLM，非逐个调用）
      ↓
④ CoverageValidator 逐 artifact 验证覆盖率 → 不过时回到③重试（max 2 rounds）
      ↓
⑤ TaskContextBuilder 为每个 task 生成 TaskContext（TaskScope + 外部契约 + 跨模块依赖）
      ↓
EnrichedWBSAssembler 总装 → wiki/tasks/enriched_wbs.json

Task Model 新增字段 (v2.1)

Task 模型新增 5 个 MDE→DEV 可追溯性字段：

字段类型说明
lld_refslist[LLDReference]指向 LLD 中具体 artifact（section + item_name + artifact_type + sub_item）
acceptance_criterialist[AcceptanceCriterion]可验证验收标准（source_section + description + verification_type + expected）
contextTaskContext?结构化上下文 — DEV Agent 直接消费，无需重读完整 LLD（含 TaskScope + external_contracts + cross_module_deps + tech_stack + upstream_artifacts）
expected_output_fileslist[str]WBS 阶段声明的预期输出文件路径
layerint分解层级: 0=model, 1=service, 2=endpoint, 3=test

REPL 多模块 WBS

REPL 到达 WBS 步骤时，自动扫描已有 LLD 文档，多模块时提供 auto_all 选项批量生成，进度显示 [1/3] ✓ module-a (12 tasks)。

设计原则：WBS 系统遵循「机械推导 + LLM 丰富」分层架构。LLDArtifactRegistry 和 DecompositionRules 是确定性的（零 LLM），LLM 仅在 EnrichedWBSAssembler 层做批处理丰富（descriptions / estimates / deps 确认），且覆盖率校验自动触发重试（max 2 rounds），确保 MDE（设计）与 DEV（实现）之间无信息丢失。

九、执行引擎

9.1 步进式执行模型

绝不自动连续执行多个步骤。每步执行后强制暂停，等待人工 approve/reject。被拒绝需返工后重新审批。
  1. 执行当前步骤任务
  2. 暂停并等待人工审批
  3. 人工决策：approve 通过 或 reject 返工
  4. 审批通过 → advance 进入下一步
  5. 重复 1-4 直至 RETRO 完成

9.2 CLI 审批命令

cogniforge status           # 查看当前状态 + 审批状态 + 操作历史
cogniforge start            # 启动工作流 / 从中断恢复
cogniforge agent <role>     # 手动执行指定 Agent → 委托给 Claude Code
cogniforge approve          # 人工审批通过当前步骤
cogniforge reject           # 拒绝 → 返工
cogniforge advance          # 审批通过后进入下一步
cogniforge wait             # 阻塞等待人工确认
cogniforge repl             # 自然语言 REPL 交互
cogniforge history          # 完整操作审计追踪

9.3 状态持久化

工作流全量状态持久化到 .cogniforge/workflow_state.json：

  • 当前步骤 + 是否等待审批
  • 每步审批记录（审批人、时间、备注、状态）
  • 每步执行结果 + 产物清单
  • 完整操作历史 timeline
中断恢复：进程退出后重新 cogniforge start 自动从上次断点恢复，无需手动干预。

解析容错

LLM 返回可能带 markdown 代码块标记（```json ... ```），REPL 自动剥离后 parse JSON。解析失败时自动重试一次。

断点恢复

REPL 启动时自动检查 .cogniforge/workflow_state.json，若已存在则从当前步骤继续。可在 REPL 和手动命令间自由切换。

TEST 分支处理

QA agent 执行后根据 data.passed 判断结果：通过则引导用户选择 UAT 或继续修复，失败则自动进入 FIX 步骤。

十三、系统特性

优势限制
可控性确定性上下文，无 RAG 不确定性文档膨胀，需持续维护
审计性Git 全量追溯，AI 操作完整记录流程复杂，学习成本高
