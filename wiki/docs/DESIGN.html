一、系统概述

1.1 背景

传统 AI Coding 的四大痛点：

  • 上下文不可控 — 依赖 RAG 导致信息遗漏与幻觉
  • 长周期不稳定 — 上下文窗口膨胀，后期产出质量急剧下降
  • 无流程约束 — vibe coding 模式不可复现、不可审计
  • 无法对齐企业研发体系 — 缺乏审批、评审、质量门禁
目标：构建一个「可持续运行」的 AI 软件开发系统，覆盖从需求到复盘的全生命周期。

1.2 全流程管线

PRD→ 架构→ 设计→ 编码→ 测试→ 上线→ 复盘

1.3 六大核心原则

Principle 1
文档即状态
所有系统状态持久化为结构化文档（Git），文档是唯一真相来源
Principle 2
无 RAG
上下文由确定性的 glob 规则加载，杜绝语义检索的不确定性
Principle 3
多 Agent 协作
8 个专职 Agent，每个只做一件事，职责边界清晰
Principle 4
DAG 驱动
13 步有向无环图定义执行流程，拓扑排序保证依赖正确
Principle 5
人工审批
每步执行后暂停，等待人工 approve/reject，绝不黑盒连续执行
Principle 6
全链路可审核
每次 AI 操作的输入、输出、推理过程完整记录，可追溯

审批约束

  • 每个 DAG 步骤执行后 强制暂停，等待人工审批
  • 审批通过 → advance 进入下一步；审批拒绝 → 返工后重新提交
  • 系统设计上 不允许自动连续执行多步

可审核性要求

  • 所有 AI 产物必须记录：输入上下文、Prompt、输出产物、推理过程、关键决策
  • 每条操作独立序列化为 JSON 审计日志文件
  • 审计日志包含：操作者角色、操作类型、耗时、状态、人工审核标记

六、Context System（无 RAG）

6.1 确定性加载规则

context = [
    "wiki/prd/prd.md",
    "wiki/sad/*.md",
    "wiki/lld/*.md",
    "wiki/decisions/*.md",
    "task.md",
    "related_code"
]

6.2 三级加载策略

Global
PRD / SAD / ADR — 全局共享，始终加载
Module
LLD + 模块代码 — 按 {module} 路由
Task
任务定义 — 按 {task_id} 路由

task → module → 加载对应路径，glob 模式匹配，路径排序保证一致性。

八、Agent 实现设计

8.1 Dev Agent

class DevAgent:
    def run(self, task):
        context = load_context(task)        # 确定性上下文加载
        code = llm.generate(context)        # 调用 LLM 适配器
        write_code(code)                    # 写入 src/{module}/
        return run_tests()                 # pytest 验证

8.2 QA Agent

class QAAgent:
    def run(self):
        generate_tests()    # 基于 LLD 生成测试用例
        execute_tests()     # 执行并生成报告

8.3 Reviewer Agent

class ReviewAgent:
    def run(self):
        return generate_cr_report()  # AI 代码评审 + 质量门禁

8.4 Tech Lead Agent（流程控制核心）

class TechLeadAgent:
    def run(self, stage):
        control_flow()        # DAG 分支决策 (TEST→FIX 或 TEST→UAT)
        evaluate_quality()    # 质量门禁检查
        decide_next_step()    # 确定下一阶段

九、执行引擎

9.1 步进式执行模型

绝不自动连续执行多个步骤。每步执行后强制暂停，等待人工 approve/reject。被拒绝需返工后重新审批。
  1. 执行当前步骤任务
  2. 暂停并等待人工审批
  3. 人工决策：approve 通过 或 reject 返工
  4. 审批通过 → advance 进入下一步
  5. 重复 1-4 直至 RETRO 完成

9.2 CLI 审批命令

cogniforge status           # 查看当前状态 + 审批状态 + 操作历史
cogniforge start            # 启动工作流 / 从中断恢复
cogniforge agent <role>     # 手动执行指定 Agent
cogniforge approve          # 人工审批通过当前步骤
cogniforge reject           # 拒绝 → 返工
cogniforge advance          # 审批通过后进入下一步
cogniforge wait             # 阻塞等待人工确认
cogniforge history          # 完整操作审计追踪

9.3 状态持久化

工作流全量状态持久化到 .cogniforge/workflow_state.json：

  • 当前步骤 + 是否等待审批
  • 每步审批记录（审批人、时间、备注、状态）
  • 每步执行结果 + 产物清单
  • 完整操作历史 timeline
中断恢复：进程退出后重新 cogniforge start 自动从上次断点恢复，无需手动干预。

十二、质量控制

12.1 人工审批门禁矩阵

阶段审批内容审批人
PRD需求文档评审PM / 产品负责人
SAD架构设计评审Architect / 技术负责人
LLD详细设计评审MDE / 模块负责人
WBS工作分解评审Tech Lead
CODING代码实现确认Reviewer
CR代码评审报告Reviewer
TEST测试结果确认QA
UAT用户验收确认产品负责人

12.2 失败处理分支

失败 → 人工决策:
  ├── fix  修复后重试 → 回到 CR
  ├── skip 跳过当前步骤
  └── stop 终止工作流

十三、系统特性

优势限制
可控性确定性上下文，无 RAG 不确定性文档膨胀，需持续维护
审计性Git 全量追溯，AI 操作完整记录流程复杂，学习成本高
可扩展Agent 插拔式架构初期搭建成本高
可持续中断恢复，长周期稳定运行不适合快速 demo
🔒

十四、安全与治理

  • RBAC — Agent 路径权限隔离，每个角色只能写 allowed_modify 路径
  • 操作日志 — 全量审计日志，不可篡改
  • Prompt 注入防护 — 输入校验，LLM 输出审查
🚀

十五、可扩展方向

  • 自动 Refactor Agent — 持续代码优化，技术债务管理
  • 多项目协同 — 跨项目依赖管理，共享组件库
  • 自进化任务生成 — 基于历史数据优化的任务拆解与调度
💡

十六、总结

本系统的本质是
AI Coding Tool → AI Software Organization
核心能力： 结构化知识 + 流程控制 + 多 Agent 协作

适用场景不适用场景

长周期持续开发单文件脚本
