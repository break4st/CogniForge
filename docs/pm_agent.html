PM Agent — 产品经理代理

类名: PMAgent(BaseAgent)  |  文件: src/cogniforge/agents/pm_agent.py (534 行)  |  角色标识: pm

1. 概述

PM Agent 是 CogniForge 工作流的起点，负责将用户需求转化为结构化的产品需求文档 (PRD)。采用 双 JSON 架构：长期状态由 prd-current.json 维护，单轮变更通过符合 RFC 6902 的 JSON Patch 表达。

设计理念：稳定 ID 体系（REQ-XXX / US-XXX）使下游代理（Architect、Design）能可靠引用需求，即使需求内容在后续迭代中变化。

3. 职责

  1. 从用户原始文本或结构化字段生成初始 PRD
  2. 为需求 (REQ-XXX) 和用户故事 (US-XXX) 分配稳定 ID
  3. 处理交互式修改——应用 JSON Patch 而非重写整个文档
  4. 针对 prd-schema.json 进行 Schema 验证
  5. 将 <created_at> 占位符替换为实际时间戳后落盘
  6. 将 PRD 渲染为 HTML 并提交到 Git
  7. 优化 DeepSeek prompt cache 命中率——JSON 结构模板位于 system prompt（固定前缀），user prompt 仅含用户输入

5. 核心流程

5.1 初始创建流程

用户输入 → run() 路由判断
  ├─ raw_text 存在 → _run_raw()
  └─ title 存在   → _run_structured()
       ↓
  构建 LLM Prompt（简洁——仅含用户输入 + 结构参考提示，JSON 模板在 ROLE_PROMPTS 中）
       ↓
  agent.generate_think_then_json() → LLM 响应
       ↓
  _extract_json() → 提取 JSON
       ↓
  _write_prd():
    1. _assign_ids() → 分配 REQ-XXX / US-XXX
    2. 确保 change_history 存在
    3. _link_stories_to_reqs() → 关联 US → REQ
    4. _validate_with_schema() → 校验 prd-schema.json
    5. 写入 .cogniforge/wiki/prd/prd-current.json
    6. render_file() → 生成 HTML
    7. git add + commit

5.2 交互式修改流程（Patch 模式）

modify_request 存在
  ↓
modify_interactive():
  1. _load_current_prd() → 读取当前 PRD
  2. 加载 pm-turn-result-schema.json
  3. 构建 system_prompt（PM 修改规则）
  4. agent.generate_interactive_patch() → LLM 输出 turn_result
  5. _extract_json() + 解析 turn_result
  6. 校验 turn_result 是否符合 pm-turn-result-schema
  7. 检查 status: no_change/need_clarification/rejected → 提前返回
  8. _apply_patches() → 使用 jsonpatch 库应用 RFC 6902 Patch
  9. 校验更新后的 PRD 是否符合 prd-schema
  10. 更新 meta.last_modified
  11. 写入、渲染 HTML、git commit

{
  "status": "updated|no_change|need_clarification|rejected",
  "message": "人类可读的变更描述",
  "operation": "modify|add|remove|reorder",
  "patches": [  // RFC 6902 JSON Patch 数组
    {"op": "add|remove|replace|move|copy", "path": "/requirements/0/name", "value": "..."}
  ],
  "open_questions": [],
  "affected_requirements": ["REQ-001", "REQ-002"],
  "new_version": 2
}

7. ID 管理策略

PM Agent 维护两套稳定 ID 体系：

  • REQ-XXX: 三位数编号（REQ-001, REQ-002...），为功能需求标识符
  • US-XXX: 三位数编号（US-001, US-002...），为用户故事标识符

_assign_ids() 方法扫描现有 ID，找到最大编号后从下一个编号开始分配。已存在的 ID 不会被重新分配。

8. LLM 调用方式

适配器：DeepSeekAdapter，基于 OpenAI SDK，端点 POST https://api.deepseek.com/v1/chat/completions

8.1 初始生成 — generate_think_then_json()

两步 API 调用：

第一步：思考分析 (thinking enabled)

POST /v1/chat/completions
	{
	  "model": "deepseek-v4-pro",
	  "messages": [
	    {"role": "system", "content": "<ROLE_PROMPTS["pm"] — 含完整 EXAMPLE JSON OUTPUT + ID 规则 + 中文要求，时间戳使用 <created_at> 占位符>"},
	    {"role": "user",   "content": "<简洁 prompt（仅用户输入 + 结构参考提示）>

请先深入分析思考，输出详细的设计方案。用自然语言描述，不要输出 JSON。"}
	  ],
	  "max_tokens": 8192,
	  "extra_body": {"thinking": {"type": "enabled"}}
	}

第二步：结构化 JSON 输出 (thinking disabled + JSON mode)

POST /v1/chat/completions
	{
	  "model": "deepseek-v4-pro",
	  "messages": [
	    {"role": "system",    "content": "<ROLE_PROMPTS["pm"]>"},
	    {"role": "user",      "content": "<简洁 prompt + 思考指令>"},
	    {"role": "assistant", "content": "<第一步的思考结果>"},
	    {"role": "user",      "content": "请将上述分析结果整理为指定的 JSON 结构输出。
只返回纯 JSON 对象，不要 markdown 代码块包裹，不要任何解释文字。"}
	  ],
	  "max_tokens": 8192,
	  "response_format": {"type": "json_object"},
	  "extra_body": {"thinking": {"type": "disabled"}}
	}

Prompt Cache 优化策略

JSON 结构模板（EXAMPLE JSON OUTPUT）位于 ROLE_PROMPTS["pm"]，作为 system message 发送。system prompt 在所有请求中完全相同，DeepSeek 的 prompt cache 可以稳定命中此前缀。user prompt 仅包含用户输入 + 一行结构参考提示：

根据以下用户描述，创建一份完整的产品需求文档 (PRD)。
	充分理解用户意图，提取项目名称、撰写详细概述、
	梳理功能需求（含验收条件）、推导用户故事、标注优先级。

	用户描述:
	{raw_text}

	参考系统提示中的 EXAMPLE JSON OUTPUT 结构输出。

时间戳字段使用 <created_at> 占位符，避免每次请求因时间戳变化导致 system prompt 内容不同。落盘时由 _write_prd() 程序化替换为实际时间。同时，_run_raw() 和 _run_structured() 不再在 prompt 中注入 {now}，避免 user prompt 前缀变化导致 cache miss。

8.4 修改模式 System Prompt（11 条规则）

你是 CogniForge 系统的 PM (Product Manager) Agent。
职责: 根据用户要求修改产品需求文档 (PRD)。
规则:
1. 不要直接输出完整文档，只输出包含 patches 数组的变更结果 JSON。
2. 保留所有已有的 REQ-ID 和 US-ID 不变。
3. 新增需求时分配新的 ID（下一个可用的 REQ-NNN / US-NNN）。
4. 直接修改需求内容（描述、验收条件、优先级等），不要更新 per-requirement
   的 version 和 change_history。change_history 只在需求首次创建时记录，
   修改轮次不追加变更历史。
5. 在 priorities 中使用需求 ID（不是需求名称）。
6. 如果检测到冲突，在 conflicts 数组中记录。
7. patches 使用 RFC 6902 JSON Pointer 格式路径。
所有文字使用中文。
传递方式：上述 11 条规则由 modify_interactive() 构造，传入 generate_interactive_patch() 的 system_prompt 参数。此前该方法错误地忽略了该参数并使用 ROLE_PROMPTS["pm"]（仅 2 行初始生成提示），现已修复为使用调用方传入的 system_prompt。generate_interactive() 回溯方案同理。

9. Schema 验证链

LLM 输出
  ↓
pm-turn-result-schema.json (turn 级别验证)
  ↓ (patches 应用后)
prd-schema.json (文档级别验证)
  ↓
写入 + HTML 渲染

验证使用 jsonschema.Draft7Validator，如果库不可用则降级跳过验证。

10. 错误处理

场景处理方式
LLM JSON 无法解析返回 status="failed"，附带原始 reasoning
PRD Schema 校验失败返回前 3 条错误信息
PRD 不存在时尝试修改返回提示需先创建 PRD
Turn result status=rejected返回 status="failed" + 拒绝原因
status=updated 但无 patches返回 status="failed"
status=need_clarification返回 open_questions 列表
