1. 概述

Design Agent (MDE — Module Design Engineer) 是 CogniForge 系统中最复杂的代理，负责为每个模块生成详细设计文档 (LLD)。它支持 5 种模块类型，每种拥有独特的所有权规则和章节要求。采用 三阶段生成架构（蓝图 → 并行分段 → 组装）和自校正循环以确保 LLM 输出质量。

设计理念：MDE 的复杂度源于"模块类型正交性"——每种 module_type（database/service/gateway/frontend/infrastructure）有完全不同的设计规则。通过 _OWNERSHIP_RULES 字典和分段 LLD schema 系统来管理这一正交性。

3. 模块类型体系

MDE Agent 支持 5 种模块类型，每种有独特的设计规则和章节：

类型唯一核心章节所有权规则
databaseindex_strategy, migration_strategy, capacity_estimation, connection_contracts所有表用 ownership=canonical，统一定义索引和迁移策略
servicedomain_objects, service_contracts, business_rules表仅 reference+derived；entity 每个属性标注 source
gatewayroute_table, middleware_chain, auth_policy, rate_limiting所有模型 ownership=owned；响应体必须完整展开
frontendcomponent_tree, state_design, route_design, interaction_flows, api_integration组件级状态模型；不定义数据库表
infrastructuretopology, message_contracts, reliability_strategy中间件数据结构（Redis/MQ/文件存储）；分 MQ/缓存/存储子类型

4. 三阶段生成架构

对于支持分段生成的模块类型，MDE 使用三阶段流水线：

阶段 1: 蓝图规划 (Blueprint)

_generate_blueprint():
  → LLM 生成顶层结构:
    - meta / source / module_boundary
    - overview / traceability
    - artifact_index (锁定所有 section 的 ID)
  → 输出: blueprint dict

阶段 2: 并行分段生成

_generate_sections_parallel():
  → ThreadPoolExecutor (最多 8 workers)
  → 每个 section 独立调用 _generate_section():
    - 传入 blueprint (确保 ID 一致性)
    - 加载对应 schema 片段 (lld-data-models.json 等)
    - 生成单个 section 的 JSON 内容
  → 收集所有 section 结果

分段分配（按模块类型）：

模块类型分段列表
servicedata_models, interfaces, error_handling, domain_objects, service_contracts, business_rules
gatewaydata_models, interfaces, error_handling, route_table
frontenddata_models, interfaces, component_tree, state_design, route_design, interaction_flows, api_integration
databasedata_models, interfaces, index_strategy, migration_strategy, capacity_estimation, connection_contracts
infrastructuredata_models, interfaces, topology, message_contracts, reliability_strategy

阶段 3: 组装 + 自校正

_assemble_lld():
  → 合并 blueprint + sections → 完整 LLD JSON
  ↓
_validate_and_commit():
  → lld_validator.validate_lld_json() → 校验
  → 未通过 → LLM 修正循环（最多 10 次）
    每次告诉 LLM 具体违反了哪条规则
  → 通过后 → 渲染 HTML + git commit
自校正循环：MDE 是唯一拥有内建自校正循环的代理。校验失败时，它会将完整校验报告反馈给 LLM 并要求修正，最多尝试 10 次。这极大提高了 LLM 输出的合规率。

5. 契约上下文构建

在生成 LLD 前，MDE 构造丰富的上下文 (_build_contract_context())：

  1. 模块自描述: 从 SAD 提取本模块的 components 定义
  2. Provider 契约: 本模块作为提供者的接口契约（签名不可修改）
  3. Consumer 契约: 本模块依赖的外部接口（引用确切签名）
  4. 邻居 LLD: 已完成的其他模块接口（交叉引用验证）
  5. 系统拓扑: 全局 layers + connections + data_flow
  6. Primary Database: 标准表的权威定义（只能 reference，不可 redefine）
  7. 全局技术栈: SAD tech_stack（限制 LLM 不可自创技术选型）

7. 交互式修改流程

mde_request 存在（由 MDERouter 生成）
  ↓
modify_interactive():
  1. 从 mde_request 提取 target_module/prd_slice/sad_slice/upstream_change
  2. 加载当前 LLD
  3. 加载 mde-turn-result-schema.json
  4. 构建 system_prompt (11 条 MDE 设计规则)
  5. agent.generate_interactive_patch() → LLM 输出 mde-turn-result
  6. 校验 → 应用 patches → 校验更新后的 LLD
  7. 写入、渲染、提交
  8. 返回 implementation_handoff + test_handoff 给下游

8. Schema 体系

MDE 的 Schema 采用基类 + 扩展的 组合模式：

schemas/agents/lld/
├── lld-base.json              # 所有模块共有的基础字段
├── lld-data-models.json       # data_models 分段 schema
├── lld-interfaces.json        # interfaces 分段 schema
├── lld-error-handling.json    # 错误处理分段 schema
├── lld-workflow.json          # 工作流分段 schema
├── lld-domain-objects.json    # service 专属: domain_objects
├── lld-service-contracts.json # service 专属: service_contracts
├── lld-business-rules.json    # service 专属: business_rules
├── lld-component-tree.json    # frontend 专属
├── lld-state-design.json      # frontend 专属
├── lld-route-design.json      # frontend 专属
├── lld-interaction-flows.json # frontend 专属
├── lld-api-integration.json   # frontend 专属
├── lld-gateway.json           # gateway 专属
├── lld-database.json          # database 专属
├── lld-infrastructure.json    # infrastructure 专属
└── lld-[其它].json

Prompt 中按模块类型动态拼装这些片段（_build_conditional_schema()）。

9. 所有权语义

MDE 强制执行三种所有权模型：

ownership含义适用模块
canonical我是唯一权威定义者；他人必须引用我仅 database
derived我引用 canonical 模型；可添加 local_extensionsservice, gateway
owned此模型完全归本模块所有所有类型
