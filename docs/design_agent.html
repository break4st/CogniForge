Design Agent (MDE) — 模块设计工程师代理

类名: DesignAgent(BaseAgent)  |  文件: src/cogniforge/agents/design_agent.py (1215行，最大文件)  |  角色标识: design

1. 概述

Design Agent (MDE — Module Design Engineer) 是 CogniForge 系统中最复杂的代理，负责为每个模块生成详细设计文档 (LLD)。它支持 5 种模块类型，每种拥有独特的所有权规则和章节要求。采用 三阶段生成架构（蓝图 → 并行分段 → 组装）和自校正循环以确保 LLM 输出质量。

设计理念：MDE 的复杂度源于"模块类型正交性"——每种 module_type（database/service/gateway/frontend/infrastructure）有完全不同的设计规则。通过 _OWNERSHIP_RULES 字典和分段 LLD schema 系统来管理这一正交性。

MDE Agent 支持 5 种模块类型，每种有独特的设计规则和章节：

类型唯一核心章节所有权规则
databaseindex_strategy, migration_strategy, capacity_estimation, connection_contracts所有表用 ownership=canonical，统一定义索引和迁移策略

4. 三阶段生成架构

对于支持分段生成的模块类型，MDE 使用三阶段流水线：

阶段 1: 蓝图规划 (Blueprint)

_generate_blueprint():
  → LLM 生成顶层结构:
    - meta / source / module_boundary
    - overview / traceability
    - artifact_index (锁定所有 section 的 ID)
  → 输出: blueprint dict

阶段 2: 并行分段生成

_generate_sections_parallel():
  → ThreadPoolExecutor (最多 8 workers)
  → 每个 section 独立调用 _generate_section():
    - 传入 blueprint (确保 ID 一致性)
    - 加载对应 schema 片段 (lld-data-models.json 等)
    - 生成单个 section 的 JSON 内容
  → 收集所有 section 结果

分段分配（按模块类型）：

模块类型分段列表
servicedata_models, interfaces, error_handling, domain_objects, service_contracts, business_rules
gatewaydata_models, interfaces, error_handling, route_table
frontenddata_models, interfaces, component_tree, state_design, route_design, interaction_flows, api_integration
databasedata_models, interfaces, index_strategy, migration_strategy, capacity_estimation, connection_contracts
infrastructuredata_models, interfaces, topology, message_contracts, reliability_strategy

阶段 3: 组装 + 自校正

_assemble_lld():
  → 合并 blueprint + sections → 完整 LLD JSON
  ↓
_validate_and_commit():
  → lld_validator.validate_lld_json() → 校验
  → 未通过 → LLM 修正循环（最多 10 次）
    1. 从 validation.meta 提取 module_type
    2. _build_fix_system_prompt(module_type) → 组装完整 schema 模板
    3. system prompt 包含：全量 JSON 结构模板 + 顶层字段白名单 + 9 条关键规则
    4. user prompt 传递完整 JSON（不截断）+ 校验报告
  → 通过后 → 渲染 HTML + git commit
自校正循环改进：修正调用的 system prompt 从原来 2 行空泛描述升级为 _build_fix_system_prompt() 动态组装的全量 schema 模板（基础模板 + 模块专属模板），含顶层字段白名单和常见错误规则，使 LLM 不再"盲修"。同时去掉了 JSON 截断（原 [:6000]），LLM 能看到完整文档。

5. 契约上下文构建

在生成 LLD 前，MDE 构造丰富的上下文 (_build_contract_context())：

  1. 模块自描述: 从 SAD 提取本模块的 components 定义
  2. Provider 契约: 本模块作为提供者的接口契约（签名不可修改）
  3. Consumer 契约: 本模块依赖的外部接口（引用确切签名）
  4. 邻居 LLD: 已完成的其他模块接口（交叉引用验证）
  5. 系统拓扑: 全局 layers + connections + data_flow
  6. Primary Database: 标准表的权威定义（只能 reference，不可 redefine）
  7. 全局技术栈: SAD tech_stack（限制 LLM 不可自创技术选型）

11. LLM 调用方式

适配器：DeepSeekAdapter，端点 POST https://api.deepseek.com/v1/chat/completions，默认模型 deepseek-v4-pro

Design Agent 是唯一使用 4 种不同调用方法的代理，覆盖全部 DeepSeek 能力。

11.1 单阶段生成 — generate_think_then_json(role="design")

两步模式（thinking→JSON），无 system prompt，max_tokens=8192，最多重试 5 次。回退方案，仅在不支持分段生成的模块类型或分段失败时使用。

Max Tokens 动态分配

所有角色的 generate_think_then_json() 调用共享同一定义于 deepseek_adapter.py 的 MAX_TOKENS_CONFIG。调用方无需传入 max_tokens，适配器根据 role 自动选择：

角色Step 1 思考 (think)Step 2 JSON (json)理由
pm16,00032,000PRD 典型 10-20 需求，每需求 ~1K token
architect20,00040,000SAD 更复杂（组件 + 契约 + 数据模型）
design24,00064,000LLD 最复杂（接口 + workflow + domain objects）

显式传入 max_tokens 仍可作为覆盖值（think 和 json 两阶段使用相同值）。

11.2 蓝图生成 — generate_messages()（system + user 双消息模式）

POST /v1/chat/completions
{
  "model": "deepseek-v4-pro",
  "messages": [
    {"role": "system", "content": "<蓝图 JSON 模板 + ID 分配规则（固定，可被 prompt cache 命中）>"},
    {"role": "user",   "content": "<模块信息 + ownership_rules + contract_context（动态数据）>"}
  ],
  "max_tokens": 4096,
  "response_format": {"type": "json_object"},
  "extra_body": {"thinking": {"type": "disabled"}}
}

JSON 模板和 ID 规则位于 system prompt 中，跨模块缓存可命中。user prompt 仅含动态模块数据。输出 meta/source/module_boundary/overview/traceability/artifact_index，后续分段必须使用蓝图锁定的 ID。

11.3 分段并行生成 — generate_messages() × N

与蓝图相同的 system + user 双消息模式，但通过 ThreadPoolExecutor (最多 8 workers) 并行执行。每个分段的 schema 模板（从 schemas/agents/lld/*.json 加载）位于 system prompt，蓝图数据位于 user prompt。分段分配按模块类型不同（service 6 段，gateway 4 段，frontend 7 段，database 6 段，infrastructure 5 段）。

11.4 校验修正 — generate_messages()

在自校正循环中使用（最多 10 轮），system prompt 由 _build_fix_system_prompt(module_type) 动态构建：

POST /v1/chat/completions
{
  "model": "deepseek-v4-pro",
  "messages": [
    {"role": "system", "content": "<\\n  = 完整 JSON 结构模板: base + data_models + interfaces + error + 模块专属 + workflow\\n  = 顶层字段白名单（按 module_type）\\n  = 9 条关键规则（data_models 必填字段、request_body 命名、ID 格式、source 类型等）\\n>"},
    {"role": "user",   "content": "你刚才生成的 LLD JSON 校验未通过：\n\n{validation_report}\n\n当前 JSON（完整，不截断）:\n{current_json}\n\n请修正以上所有问题，返回完整的修正后 JSON。\n只返回纯 JSON 对象，不要 markdown 代码块包裹。"}
  ],
  "max_tokens": 8192,
  "response_format": {"type": "json_object"},
  "extra_body": {"thinking": {"type": "disabled"}}
}

改进历史：v1 版本 system prompt 仅 2 行空泛描述（"输出格式请参照 system prompt 中的 EXAMPLE JSON OUTPUT 示例"），user prompt 中 JSON 截断到 6000 字符。LLM 在无 schema 上下文的情况下"盲修"，导致修正循环频繁耗尽 10 次上限。v2 版本改为传递完整 schema 模板 + 白名单 + 规则清单，JSON 不再截断。

11.5 交互式修改 — generate_interactive_patch()

两步模式，注入 MDE 角色，分析上游变更对 LLD 的影响后输出 patches。修改模式 System Prompt（11 条规则）：

你是 CogniForge 系统的 MDE (Design) Agent。
职责: 维护模块 '{module}' ({module_type}) 的详细设计文档 (LLD)。
规则:
1. 不要直接输出完整 LLD 文档，只输出包含 patches 数组的变更结果 JSON。
2. 保留所有已有的 DM-ID、IF-ID、DO-ID、SC-ID 不变。
3. 新增对象时分配新的 ID（下一个可用编号）。
4. 修改已有对象时，version +1 并追加 change_history。
5. 你只能设计本模块范围内的内容，不可越界设计其他模块。
6. SAD contract 由本模块实现时，在 interfaces[] 中建立对应 interface 并填写 source_contract_id。
7. 只消费 contract 时，在 api_integration/connection_contracts 中引用。
8. SAD contract 不完整或不一致时，不可擅自修改——在 upstream_issues 中反馈。
9. 每次 LLD 有变化，meta.version +1。
10. patches 使用 RFC 6902 JSON Pointer 格式路径。
11. 在 implementation_handoff 和 test_handoff 中给出下游任务提示。
所有文字使用中文。

11.6 Design Agent 专属 System Prompt

ROLE_PROMPTS["design"] 包含 ~170 行的完整 LLD JSON 示例，覆盖所有 5 种模块类型的字段结构。在 generate_think_then_json() 和 generate_messages() 中被注入到 system prompt。
