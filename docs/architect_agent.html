Architect Agent — 系统架构师代理

类名: ArchitectAgent(BaseAgent)  |  文件: src/cogniforge/agents/architect_agent.py (680 行)  |  角色标识: architect

1. 概述

Architect Agent 负责将 PRD 转化为系统架构文档 (SAD)。采用 双 JSON 架构：长期状态由 sad-XXX.json 维护，单轮变更通过 se-turn-result-schema.json 管控。通过一致性检查机制确保架构与需求的持续对齐。

设计理念：Architect 不仅生成初始架构，还持续跟踪 PRD 变更对架构的影响——优先复用现有组件，仅在必要时新增。所有架构元素（组件、契约、数据模型）均有稳定 ID，向下游代理提供可靠引用锚点。

3. 职责

  1. 从 PRD 生成系统架构文档 (SAD)
  2. 维护组件 (CMP-XXX)、契约 (CTR-XXX)、数据模型 (DM-XXX) 三套稳定 ID 体系
  3. 在架构的各分层（layers）中组织组件，定义层间通信协议
  4. 处理交互式修改——根据 PM 变更分析架构影响
  5. 运行一致性检查（consistency_checks）确保 SAD 与 PRD 对齐
  6. 生成 downstream_handoff 指导 MDE、Dev、QA 等下游代理

5. 核心流程

5.1 初始 SAD 生成

_run_generate_initial():
  1. _load_latest_prd() → 读取 PRD 作为源输入
  2. 确定 doc_id 和 version（检查是否已有 SAD）
  3. 构建详细 LLM prompt（含完整 JSON 结构模板）
     - system_overview.roles: 从 PRD 提取用户角色及权限
     - architecture.layers: 分层拓扑（接入层→网关→服务层→数据层）
     - components[]: 每个含 id/type/status/source_requirements/change_history
     - contracts[]: 每个含 provider_component_id/endpoint/request/response/errors
     - data_models[]: 每个含 fields 数组
     - requirement_traceability[]: 每条 PRD 需求的覆盖追踪
  4. agent.generate_think_then_json() → LLM 响应
  5. repair_truncated_json() → 修复截断的 JSON（最多重试 2 次）
  6. _assign_ids() → 分配 CMP-XXX / CTR-XXX / DM-XXX
  7. 组件类型正规化 (_normalize_component_type)
  8. _commit_and_result() → 写入、渲染 HTML、git commit

5.2 交互式修改流程

pm_turn_result 存在
  ↓
modify_interactive():
  1. _load_current_sad() → 读取当前 SAD
  2. _load_latest_prd_dict() → 读取当前 PRD (全量)
  3. 加载 se-turn-result-schema.json
  4. 构建 system_prompt (15 条架构治理规则):
     - 优先复用现有组件
     - 修改已有 component 时 version+1 + change_history
     - 每个 active requirement 必须有 coverage 记录
     - SAD 有变化时 meta.version+1
     - 默认不删除，用 status=deprecated/removed
     - 在 downstream_handoff 中给出下游 Agent 提示
  5. agent.generate_interactive_patch() → LLM 输出 se-turn-result
  6. 校验 turn_result 是否符合 se-turn-result-schema
  7. 检查 status: no_change/need_clarification/rejected → 提前返回
  8. _apply_patches() → 应用 RFC 6902 JSON Patch
  9. 校验更新后的 SAD 是否符合 sad-schema
  10. run_all() → 一致性检查（consistency_checks）
  11. 写入、渲染 HTML、git commit

8. 一致性与重试

  • JSON 截断修复：使用 repair_truncated_json() 修复 LLM 输出被截断时的 JSON 结构（最多重试 2 次）
  • 一致性检查：修改模式下调用 cogniforge.consistency_checks.run_all()，验证 PRD 需求与 SAD 组件/契约之间的覆盖关系
  • 原子写入：通过 git_storage.atomic_write() 确保 JSON + HTML 的 Git 提交为原子操作

9. LLM 调用方式

适配器：DeepSeekAdapter，基于 OpenAI SDK，端点 POST https://api.deepseek.com/v1/chat/completions，默认模型 deepseek-v4-pro

9.1 初始 SAD 生成 — generate_think_then_json(role="architect")

两步 API 调用，与 PM 相同模式但 无 system prompt，SAD JSON 结构模板内嵌于 user prompt：

第一步：思考分析

POST /v1/chat/completions
{
  "model": "deepseek-v4-pro",
  "messages": [{
    "role": "user",
    "content": "<SAD JSON 结构模板 + PRD 上下文 + 组件/契约/数据模型规则>\n\n请先深入分析思考，输出详细的设计方案。用自然语言描述，不要输出 JSON。"
  }],
  "max_tokens": 8192,
  "extra_body": {"thinking": {"type": "enabled"}}
}

第二步：结构化 JSON

POST /v1/chat/completions
{
  "model": "deepseek-v4-pro",
  "messages": [
    {"role": "user",      "content": "<原始 prompt>"},
    {"role": "assistant", "content": "<第一步的思考结果>"},
    {"role": "user",      "content": "请将上述分析结果整理为指定的 JSON 结构输出。\n只返回纯 JSON 对象，不要 markdown 代码块包裹，不要任何解释文字。"}
  ],
  "max_tokens": 8192,
  "response_format": {"type": "json_object"},
  "extra_body": {"thinking": {"type": "disabled"}}
}

重试机制：JSON 解析失败时最多重试 2 次，每次将错误信息反馈给 LLM 重新生成。repair_truncated_json() 用于修复截断的 JSON。

两步 API 调用，注入 SE 角色 + 分析 SAD 变更影响：

第一步：分析 + 规划 Patches

  "response_format": {"type": "json_object"},
  "extra_body": {"thinking": {"type": "disabled"}}
}

9.3 修改模式 System Prompt（12 条架构治理规则）

你是 CogniForge 系统的 SE (Architect) Agent。
职责: 根据 PRD 变更维护系统架构文档 (SAD)。
规则:
1. 不要直接输出完整 SAD 文档，只输出包含 patches 数组的变更结果 JSON。
2. 保留所有已有的 CMP-ID、CTR-ID、DM-ID 不变。
3. 新增组件/契约/数据模型时分配新的 ID（下一个可用的编号）。
4. 修改已有 component/contract 时，version +1 并追加 change_history。
5. 优先判断现有组件是否能承载新需求，不要默认新增组件。
6. 每个 active requirement 必须在 requirement_traceability 中有覆盖状态。
7. SAD 有变化时 meta.version +1。
8. 如果 PRD 需求无法被当前架构覆盖，返回 coverage=partial/blocked。
9. 如果接口契约缺少 request/response/provider_component_id，必须补齐。
10. 默认不删除，用 status=deprecated/removed 标记。
11. patches 使用 RFC 6902 JSON Pointer 格式路径。
12. 在 downstream_handoff 中给出 BE/FE/QA/DevOps agent 的任务提示。
所有文字使用中文。

10. 与下游代理的交互

下游代理交互方式
DesignAgent (MDE)SAD 的 components/contracts 被 MDE Router 用于扇形分发；module_boundary 中的 owned_components/owned_contracts 直接引用 SAD ID
TechLeadAgentSAD 的组件拓扑用于 WBS 任务分解的模块分组
DevOpsAgentSAD 的 tech_stack/infrastructure 配置用于部署配置生成
