概述

Message Queue
RabbitMQ消息队列基础设施，用于异步解耦部署编排服务与SSH执行服务，支持任务可靠投递、失败重试和死信处理。定义系统消息拓扑（Exchange/Queue/Binding）、消息契约和投递策略，保障部署任务不丢失、不重复消费。
依赖: Deployment OrchestratorSSH Execution Service
RabbitMQDocker 容器化部署

错误处理

RabbitMQ消息队列的错误处理分为四个层面： (1) 连接层 — 服务启动时自动初始化RabbitMQ连接，启用连接恢复机制（automatic_recovery），在连接断开时自动重连（重试间隔5秒）。连接长时间不可达时记录ERROR日志并触发运维告警通知排查。 (2) 投递层 — 生产者启用publisher confirms机制（confirm_select），在消息确认回调中处理投递结果：Broker返回basic.ack表示投递成功；Broker返回basic.nack或投递超时（默认5秒超时阈值）表示投递失败，由生产者重试最多3次后仍失败则记录错误日志并标记部署状态为failed。 (3) 消费层 — 消费者采用手动确认模式（manual_ack），按消息处理结果执行不同确认操作：处理成功调用basic_ack确认消费，消息正式出队；可恢复类型异常（如SSH连接超时、远程命令执行失败）调用basic_nack(requeue=false)拒绝消息，通过死信机制转入deployment.retry重试队列等待30秒后重新投递；不可恢复类型异常（如消息格式错误、必需字段缺失）直接basic_ack确认消费丢弃消息，防止死信队列无限堆积；消费者进程崩溃或TCP连接断开时，Broker自动将已投递但未确认的unacked消息重新入队（requeue=true），由其他消费者或重连后的同一消费者重新消费。 (4) 重试与死信层 — 消息处理失败后的流转策略采用'重试队列+TTL+死信'的延迟重试模式：第1次失败后消息路由到deployment.retry队列等待30秒TTL超时，过期后自动投递到cogniforge.deployment Exchange重新回到deployment.execute队列重新消费；第2次失败重复上述流程且retry_count递增为2；第3次失败retry_count递增为3；当retry_count >= 3时消息不再转入重试队列而是路由到deployment.dlq死信队列，不再自动重试，由运维人员通过RabbitMQ Management Plugin（管理端口15672）查看死信详情、排查错误原因后手动决定重新投递或丢弃。每条消息的retry_count字段由消费者检测到异常后在nack前写入消息头，重试队列只做TTL延迟转发，不修改消息体内容。
