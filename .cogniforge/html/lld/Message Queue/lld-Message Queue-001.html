概述

模块: Message Queue

消息队列中间件，用于异步任务处理，解耦核心业务与统计计算。消息队列以独立中间件形态存在，被 Statistics Service 及上游业务服务通过消息客户端程序化接入（不暴露 REST 接口）。当前核心消息为统计计算任务——当业务操作（如学习数据录入、学生/班级/年级归属变更等）触发统计需求时，上游服务发送消息到 topic: statistics.calculation，Statistics Service 异步消费并执行统计计算。消息队列提供基于主题（Topic）的发布-订阅模型，支持多个生产者和消费者。消息投递采用至少一次语义（at-least-once），消费者需幂等处理。消费失败的消息支持重试机制，超过最大重试次数后自动转入死信队列（DLQ）。消息体采用 JSON 序列化。中间件选型建议使用 RabbitMQ（作为独立服务部署）或 Redis Stream（轻量方案，与现有 Redis 复用基础设施），后续根据实际吞吐量需求可切换为 Kafka。

🗄️

数据模型 (4)

topic_config

字段类型描述
statistics.calculationtopic统计计算任务主题。业务操作（学习数据录入、学生/班级/年级归属变更等）触发统计需求时，上游服务向此主题发送消息。Statistics Service 订阅此主题并异步消费。消息内容包含 task_type（统计维度：student|class|grade）、entity_id（统计对象 ID）、action（动作：recalculate|refresh）、triggered_at（触发时间）。采用直接交换机模式（RabbitMQ Direct Exchange）或单一 Stream（Redis Stream），确保消息路由到对应消费者。

message_schema

字段类型描述
message_idstring (uuid)消息全局唯一 ID，由生产者生成，格式为 UUID v4。用于消费者幂等去重和追踪。消息整个生命周期中保持不变。
topicstring目标主题名称，如 statistics.calculation。生产者发送时指定，消息队列根据此字段路由消息。
body.task_typestring任务类型枚举: student|class|grade。标识统计维度——student 按学生维度统计、class 按班级维度统计、grade 按年级维度统计。必填，不可为空。
body.entity_idnumber统计对象 ID。对应 student_id/class_id/grade_id，与 task_type 组合确定统计范围和对象。必填，不可为空。
body.actionstring动作枚举: recalculate|refresh。recalculate 表示全量重新计算，refresh 表示增量刷新（当前先按全量重算实现）。必填，不可为空。
body.triggered_atstring (datetime)任务触发时间戳，格式为 ISO 8601（如 2026-05-20T13:56:00+08:00）。用于记录任务触发时间，支持后续审计和延迟分析。必填，不可为空。
headers.retry_countnumber消息当前已重试次数。初始值为 0，每次重新投递时由 MQ 系统自增。消费者可读取此值进行重试感知处理（如记录重试日志）。
headers.created_atnumber (timestamp)消息原始创建时间戳（Unix 毫秒）。用于计算消息存续时间和检测消息积压，消费者可据此判断消息是否已超期。

dlq_config

字段类型描述
dlx_exchangestring死信交换机名称（RabbitMQ）：dlx.statistics。用于接收统计任务主题的死信消息。
dlq_queuestring死信队列名称（RabbitMQ）：dlq.statistics.calculation。死信消息的存储队列。
max_retrynumber消息最大重试次数，默认 3。重试次数（含首次失败后的重新投递）达到此上限后消息转入 DLQ。
dlq_message_ttlnumber死信消息存活时间（秒），默认 86400（24 小时）。超过 TTL 的消息自动丢弃，避免 DLQ 无限积压。
dlq_alert_thresholdnumberDLQ 消息数量告警阈值，默认 10。当 DLQ 中积压消息数超过此阈值时触发告警通知（如发送到监控系统或日志告警）。

retry_policy

字段类型描述
initial_intervalnumber首次重试间隔（秒），默认 5。首次消费失败后等待 5 秒重新投递。
multipliernumber退避倍数，默认 2。每次重试间隔翻倍：5 秒 → 10 秒 → 20 秒。
max_intervalnumber最大重试间隔（秒），默认 60。重试间隔不超过此值。
max_retrynumber最大重试次数，默认 3。超过此次数后消息转入 DLQ（死信队列）。

接口定义 (4)

统计任务消息队列（provider）

topic: statistics.calculation

业务操作触发统计任务时，上游服务向此主题发布消息。本接口为 MQ 的生产者接口定义，上游服务（如 Statistics Service 自身录入学习数据后）调用此接口发送消息。消息体包含 task_type、entity_id、action、triggered_at 四个必填字段。消息发送采用异步非阻塞方式，不阻塞业务主流程。发送失败（如 MQ 不可用）记录 WARN 日志，业务操作不回滚——统计任务待 MQ 恢复后通过补偿机制重新发送。

参数类型描述
task_typestring任务类型枚举: student|class|grade，标识统计维度
entity_idnumber统计对象 ID，对应 student_id/class_id/grade_id
actionstring动作枚举: recalculate|refresh，标识全量重算或增量刷新
triggered_atstring (datetime)任务触发时间戳，ISO 8601 格式

消息队列客户端配置

MQ Client Connection

消息队列客户端连接配置与初始化。各微服务通过 MQ 客户端连接池（或长连接）与消息队列交互。连接配置包含：Broker 地址列表、虚拟主机（vhost）、认证凭据、心跳间隔和网络超时参数。消费者和生产者复用同一连接配置，但分别创建独立的 Channel（RabbitMQ 模型）或 Consumer Group（Redis Stream 模型）。消费者启动时注册消息处理器并开始监听队列。连接异常时客户端应自动重连并恢复订阅。

参数类型描述
hoststring消息队列服务器主机地址（或节点列表）
portnumber消息队列服务端口，RabbitMQ AMQP 默认为 5672，Redis Stream 沿用 Redis 6379
vhoststring虚拟主机（仅 RabbitMQ），用于多环境隔离，开发/测试/生产使用不同 vhost
usernamestring连接认证用户名
passwordstring连接认证密码
heartbeatnumber心跳间隔（秒），默认 60，用于检测连接是否存活
connection_timeoutnumber连接超时（毫秒），默认 5000
prefetch_countnumber消费者预取数量，默认 1（每次只消费一条，处理完毕确认后才投递下一条），控制并发消费不堆积

消息发布接口（Producer）

MQ Publish {topic}

向指定主题发布消息的核心接口。由各生产者在业务逻辑中调用。核心逻辑：1）创建消息体 JSON：包含 message_id（UUID v4）、topic、body（task_type、entity_id、action、triggered_at）和 headers（retry_count=0、created_at=当前时间戳）；2）调用 MQ 客户端 basic_publish（RabbitMQ）或 XADD（Redis Stream）将消息发送到指定主题；3）发送成功返回消息 ID（用于后续追踪）；4）发送失败（MQ 连接断开或 Broker 拒绝）时，记录 WARN 日志并尝试重连后重试一次；5）重试仍失败则记录 ERROR 日志（不阻塞业务主流程）；6）支持批量发布（可选），便于批量导入等场景。

参数类型描述
topicstring目标主题名称，当前仅 statistics.calculation
message_bodyobject消息业务负载，包含 task_type、entity_id、action、triggered_at
delay_msnumber (optional)消息延迟投递（毫秒），默认 0。用于延迟队列场景，当前不需延迟，预留扩展。

消息消费接口（Consumer）

MQ Consume {topic} -> callback

从指定主题消费消息的核心接口。消费者注册回调处理器，MQ 客户端自动拉取消息并调用处理器。核心逻辑：1）消费者启动时建立连接并订阅 statistics.calculation 主题；2）注册消息处理器 handle_message(message)；3）MQ 客户端按 prefetch_count 拉取消息投递给处理器；4）处理器反序列化 JSON，解析 task_type、entity_id、action、triggered_at；5）处理成功后调用 basic_ack（RabbitMQ）或 XACK（Redis Stream）确认消息，MQ 删除已确认消息；6）处理失败不确认（nack）——MQ 根据重试策略重新投递。核心约束：消费者必须幂等处理——同一消息可能因网络抖动被重复投递，消费者应基于 message_id 或 (task_type, entity_id) 组合实现幂等控制。当前消费者：Statistics Service。

参数类型描述
topicstring订阅的主题名称，当前为 statistics.calculation
consumer_tagstring消费者标识，格式为 {service}.{host}.{pid}，用于监控和排障
prefetch_countnumber预取消息数，默认 1，确保消息均匀分配
auto_ackboolean是否自动确认，默认 false（手动确认），确保消费失败时消息不丢失
⚠️

错误处理

Message Queue 按以下规则处理异常：1）消息发送失败——生产者调用发布接口时 MQ 连接异常或 Broker 拒绝，立即尝试重连后重试一次，重试仍失败则记录 ERROR 日志"消息发送失败"（包含 topic、message_id、body 摘要），不阻塞业务主流程，业务操作正常完成，统计任务通过后续补偿机制（定时扫描或下次触发时）重新计算；2）消息消费异常——消费者处理消息时抛出异常，不确认消息（basic_nack 且 requeue=true），MQ 根据重试策略重新投递：首次重试间隔 5 秒，二次 10 秒，三次 20 秒（指数退避），每次重新投递时 headers.retry_count 自增；3）消费重试耗尽——消息重试 3 次后仍然失败，执行 basic_nack 且 requeue=false（不重新入队），消息自动转入死信队列 DLQ，记录 ERROR 日志"消息已转入死信队列"（包含 message_id、task_type、entity_id、重试次数），触发 DLQ 告警（DLQ 消息数超过 10 时通知运维人员介入排查）；4）消息体格式异常——消费者反序列化消息 JSON 失败（格式错误、必填字段缺失、类型不匹配），直接确认消息并丢弃（避免坏消息阻塞队列），记录 WARN 日志"消息格式非法，已丢弃"（包含 message_id 和原始内容）；5）消息重复投递——MQ 的 at-least-once 语义可能导致消息重复，消费者需幂等处理：基于 message_id 缓存已成功处理的消息 ID（缓存 TTL 设为 30 分钟），重复消息直接确认后丢弃，不重复执行统计计算；6）MQ 连接中断——消费者检测到与 Broker 的连接中断后，自动重连（指数退避，最大间隔 30 秒），重连成功后自动恢复队列订阅并继续消费，记录 WARN 日志"MQ 连接已断开，正在重连..."和 INFO 日志"MQ 连接已恢复"；7）消息积压——消费者处理速度跟不上生产速度导致消息积压时，记录 WARN 日志"消息队列积压：{queue_name} {message_count} 条未消费"，积压超过阈值（暂定 1000 条）时触发告警，可考虑临时增加消费者实例数或独立排查消费者瓶颈；8）生产者消息丢失——如使用 Redis Stream 作为 MQ，在 Redis 主从切换（failover）且未启用同步持久化时可能丢失未消费消息，此风险通过日志追踪并在后续迭代中引入消息表持久化兜底策略来解决；9）死信消息处理——运维人员定期（每日）检查 DLQ，分析消费失败原因，修复问题后手动将死信消息重新投递到原队列重试，死信消息在 DLQ 中的 TTL 为 24 小时，超期自动丢弃。所有操作记录结构化日志，生产者日志包含操作（publish）、topic、message_id、body 摘要（不记录完整 body 以防敏感信息泄露）和耗时；消费者日志包含操作（consume）、topic、message_id、task_type、entity_id、重试次数和处理结果（success/retry/dead），日志级别：正常消费 INFO，发送/消费失败 WARN，超出重试次数/格式异常/积压告警 ERROR。
