概述

脚本生成引擎
⚙️ 业务服务
根据部署配置自动生成远程服务器的启动脚本、健康检查脚本和服务注册脚本。根据项目类型（Go二进制/Java JAR/Node.js/Python等）选择对应的标准脚本模板，注入环境变量和启动参数，生成systemd服务注册文件和健康检查脚本，支持用户自定义前置/后置脚本扩展。生成的脚本内容通过内部API返回给部署编排服务，由远程命令执行器写入部署目录并执行。
依赖: 部署编排服务远程命令执行器
GoGin

🔢 ProjectType枚举

项目类型枚举，决定使用哪个模板集合生成脚本

值
go_binary — Go语言编译的二进制可执行文件，直接启动 java_jar — Java JAR包，使用 java -jar 启动 nodejs — Node.js 应用，使用 node 或 npm start 启动 python — Python 应用，使用 python 或 gunicorn/uvicorn 启动 custom — 用户完全自定义的启动方式

🔢 ScriptType枚举

脚本类型枚举，标识每个生成脚本的用途和生命周期阶段

值
startup — 应用启动脚本，设置环境变量、cwd、执行启动命令并记录PID shutdown — 应用停止脚本，根据PID优雅终止进程 healthcheck — 健康检查脚本，通过端口/TCP/HTTP探测应用状态 service_registration — 服务注册配置（systemd unit），实现开机自启和进程托管 pre_hook — 用户自定义前置钩子，在启动前执行（如数据库迁移） post_hook — 用户自定义后置钩子，在停止后执行（如清理缓存）

服务接口 (1)

🔧 ScriptGeneratorService 5 方法
GenerateAllScripts
(request: ScriptGenerationRequest) -> ScriptGenerationResult
生成全套部署脚本，包含启动、停止、健康检查和服务注册脚本。按固定顺序生成：停止脚本 → 启动脚本 → 健康检查脚本 → 服务注册脚本（如有配置）→ 自定义钩子脚本（按order排序）。每类脚本按 projectType 选择对应模板渲染。
前置条件
request.projectType 是已注册的 ProjectType 枚举值；request.deployPath 非空且格式化为绝对路径（以/开头）；request.appName 非空
后置条件
返回值 ScriptGenerationResult.scripts 至少包含一个 startup 类型的脚本；所有脚本的 checksum 与正文内容匹配；对相同的 request 反复调用返回语义相同的内容（幂等性）；result.generatedAt 按服务器时钟返回
UnsupportedProjectTypeError→ 400request.projectType 不在已注册的 ProjectType 枚举中TemplateRenderError→ 400模板渲染时发现未定义的占位符或模板语法错误CustomHookValidationError→ 400自定义钩子脚本未通过语法安全检查（如高风险命令或shebang缺失）InternalTemplateError→ 500内置模板运行时报错或自定义模板加载失败
GenerateStartupScript
(request: ScriptGenerationRequest) -> GeneratedScript
仅生成启动脚本，不连带生成其他类型脚本。启动脚本结构：shebang → 环境变量导出段 → 目录切换 → PID文件声明 → nohup启动或systemd-run调用 → PID记录
前置条件
request.deployPath 非空；request.appName 非空；request.projectType 合法
后置条件
返回值.GeneratedScript.scriptType == ScriptType.startup；返回值.GeneratedScript.executable == true；脚本内容包含完整的 shebang（#!/bin/bash）和环境变量注入段
UnsupportedProjectTypeError→ 400不支持的projectTypeTemplateRenderError→ 400占位符渲染失败
GenerateHealthCheckScript
(request: ScriptGenerationRequest) -> GeneratedScript
生成健康检查脚本。Go二进制和Java JAR项目使用 /proc/net/tcp + PID文件双重确认；Node.js/Python项目使用 curl/wget 请求应用HTTP端点确认。脚本以 exit code 0/非0 表示健康/不健康。
前置条件
request.port 在 1-65535 范围内；request.appName 非空
后置条件
返回值.GeneratedScript.scriptType == ScriptType.healthcheck；脚本根据 projectType 使用对应的探测方式（如 Go二进制和Java JAR使用端口检测，Node.js使用HTTP /health 端点）
UnsupportedProjectTypeError→ 400不支持的projectTypeInvalidPortError→ 400port 为空或不在 1-65535 范围内TemplateRenderError→ 400模板渲染失败
GenerateServiceRegistrationScript
(request: ScriptGenerationRequest) -> GeneratedScript
生成 systemd service unit 文件内容。包含 [Unit] 段（Description/After）、[Service] 段（ExecStart/WorkingDirectory/Restart/User）、[Install] 段（WantedBy）。脚本文件由远程命令执行器写入 /etc/systemd/system/ 目录并执行 systemctl daemon-reload。
前置条件
request.serviceConfig 非空且 serviceConfig.serviceName 非空
后置条件
返回值.GeneratedScript.scriptType == ScriptType.service_registration；返回值.GeneratedScript.name 包含 serviceConfig.serviceName 作为文件名前缀
InvalidServiceConfigError→ 400serviceConfig 为 nil 或 serviceName 为空TemplateRenderError→ 400模板渲染失败
PreviewScript
(request: ScriptGenerationRequest, scriptType: ScriptType) -> String
预览指定类型的脚本渲染结果。部署编排服务可在部署前调用此接口将脚本内容展示给用户确认，确认无误后再执行实际部署。此方法纯计算，无副作用。
前置条件
request.projectType 合法；scriptType 对应的模板存在
后置条件
返回的字符串是完整渲染后的脚本正文，与写入文件的内容一致；不修改任何系统状态
UnsupportedProjectTypeError→ 400不支持的projectTypeUnsupportedScriptTypeError→ 400参数 scriptType 对应的模板不存在TemplateRenderError→ 400模板渲染失败
数据访问依赖
FindScriptTemplate(projectType: ProjectType, scriptType: ScriptType) -> ScriptTemplate? — 查询指定项目类型和脚本类型的模板，返回 nil 时回退到内置模板
FindCustomHooks(environmentId: string) -> []CustomHookConfig — 查询指定环境的自定义钩子列表，按 order 升序返回

业务规则

不变量
  • !所有生成的脚本必须包含完整的 shebang 行（#!/bin/bash），保证在远程服务器上可直接解释执行
  • !脚本必须幂等——对同一部署目录重复生成和执行不产生冲突（启动前先停止已有进程、目录存在不报错）
  • !敏感环境变量（sensitive=true）在脚本中以引用的脱敏占位符注入，不以明文值直接写入脚本正文
  • !自定义钩子脚本不能包含 rm -rf /、mkfs、dd if=/dev/zero 等高危命令，校验阶段拒绝生成
  • !所有生成的脚本文件名在同一个部署上下文中必须唯一
跨服务规则
脚本内容必须与远程命令执行器预期的目录结构一致——deployPath 对应部署目录，logPath 对应日志目录，PID文件写入 deployPath
生成的 systemd service 文件必须由远程命令执行器写入 /etc/systemd/system/ 目录并执行 systemctl daemon-reload，脚本生成引擎不直接操作远程文件系统
部署编排服务应在调用 GenerateScripts 前先验证所有输入的合法性和完整性，避免在执行层才暴露参数错误
脚本模板的版本更新（新增占位符或修改模板结构）必须同步更新部署编排服务的 ScriptGenerationRequest 组装逻辑，保持契约一致性

错误处理

处理策略

脚本生成错误统一捕获并转换为结构化错误响应返回给部署编排服务。模板在服务启动时预编译验证，内置模板语法错误在启动阶段即暴露，不延迟到运行时。变量占位符解析失败时返回具体未匹配的占位符名称，便于快速定位问题。自定义钩子脚本在注入前执行基础语法检查（shebang合法性、shell语法简单校验）。生成流程为纯计算无副作用，出错时不会对远程服务器产生任何影响，调用方可安全重试。

统一错误响应体
字段类型
codeinteger(HTTP状态码或自定义业务码)
errorstring(错误分类标识)
detailstring(详细错误描述，包含具体占位符或模板名称)

500

自定义模板从配置文件加载失败（文件不存在、格式错误或权限不足）。处理方式：返回500，detail字段包含文件路径和具体错误原因，触发运维告警。
