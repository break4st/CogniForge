概述

部署执行服务
⚙️ 业务服务
核心部署引擎，负责接收部署请求并创建部署任务、通过SSH连接池建立远程连接、在远程服务器创建版本目录、上传可执行文件、自动生成启动/停止/重启脚本、更新部署状态和进度反馈
依赖: PostgreSQL数据库SSH连接池密钥管理服务审计日志服务
PythonFastAPIparamikoPostgreSQL 15

业务规则

不变量
  • !每个部署任务必须关联到一个有效的项目和一个存在的部署环境，project_id 和 environment_id 都必须在各自表中存在对应记录
  • !同一项目和环境的版本号应保持递增趋势，不允许对同一环境部署比上次部署版本号更低或相同的版本（强制版本递进）
  • !部署任务的 status 转换必须严格遵循状态机定义，不允许跳过中间状态或逆向转换
  • !部署步骤的 step_order 从 1 开始递增且无跳跃，所有步骤按顺序串行执行，不允许并行执行
  • !部署日志（logs 字段）由所有步骤的 output 按执行顺序拼接而成，不得丢失或重排任何步骤的输出
  • !部署失败时 error_message 必须包含明确的错误原因和上下文，至少精确到失败的部署步骤
状态机
🎯 Deployment
pendingrunningsuccessfailed
→系统开始执行部署流程by system
→所有部署步骤全部执行成功by system
→任意部署步骤执行失败或用户取消部署by system
🚫 success 状态不可逆，已成功的部署任务不允许回退到 running 或 pending🚫 failed 状态不可逆，已失败的部署任务不允许回退到 running 或 pending，需创建新部署重试
⚡ 同一 environment_id 下最多允许一个 running 状态的部署任务，通过数据库查询约束确保。创建新部署时先查询该环境是否有 running 状态的记录，如有则返回 ConcurrentDeploymentLimitError。状态更新使用乐观锁（updated_at 比对）防止并发覆盖
🎯 DeploymentStep
pendingrunningsuccessfailed
→系统开始执行该步骤by system
→步骤执行成功by system
→步骤执行失败by system
🚫 success 状态不可逆，步骤执行成功后不会重新执行🚫 failed 状态不可逆，步骤失败后整个部署标记为 failed，不会重试失败的步骤
⚡ 步骤按 step_order 严格串行执行，当前一个步骤状态变为 success 后下一个步骤才从 pending 切换到 running
跨服务规则
部署执行前必须通过密钥管理服务的「密钥解密（内部）」接口（POST /api/internal/keys/decrypt）解密 SSH 私钥，解密后的私钥仅存于内存中，使用后立即清除，禁止写盘或持久化
每次部署状态变更（创建/开始/成功/失败/取消）必须调用审计日志服务「记录审计日志（内部）」接口（POST /api/internal/audit-logs）记录操作轨迹，resource_type 固定为 deployment，action 格式为 deployment.create / deployment.start / deployment.success / deployment.failed / deployment.cancel
SSH 连接从 SSH 连接池获取后，在部署执行完成后必须调用「释放连接」接口归还到连接池，防止连接泄漏
获取 SSH 连接时传入的主机地址、端口、用户名、密钥引用 ID 必须与目标环境（environments 表）的配置严格一致
部署过程中引用的项目和环境配置可能在部署排队期间被其他服务删除或修改，因此在进入 running 状态前应再次校验环境配置的完整性和可用性

错误处理

处理策略

部署执行服务采用分层错误处理策略：请求校验失败返回 4xx 错误码及具体校验信息；SSH 连接/文件传输/脚本生成等执行阶段错误返回 5xx 并记录详细错误到 deployment_steps；密钥解密失败视为致命错误立即终止部署并将状态置为 failed；所有关键操作均通过审计日志服务记录以供追溯
