概述

模块: Redis

Redis 作为系统内存缓存与发布订阅中间件，位于数据层。核心职责包括：缓存部署实时状态供 WebSocket 推送消费、管理 WebSocket 连接会话、缓存热点环境配置数据以减少 MySQL 读压力、通过发布订阅模式实现部署状态变更的实时通知。Redis 部署采用主从架构保证高可用，所有缓存键使用统一命名空间前缀，按业务模块分层设计 TTL 策略，避免内存无限增长。Redis 不可用时各服务降级为直读 MySQL，保证系统核心功能不中断。

DeploymentCache

部署实时状态缓存接口。部署编排服务写入和读取部署状态，SSH 执行代理回写进度。前端通过 WebSocket 间接读取。

ConfigCache

Redis::ConfigCache

环境配置热点缓存接口。部署编排服务在触发部署前读取缓存的连接配置；环境管理服务在配置更新后主动淘汰缓存。采用 Cache-Aside 模式：读时 MISS 则回源 MySQL 并回填缓存，写时主动删除缓存。

RateLimiter

Redis::RateLimit

API 网关请求速率限制接口。基于 INCR + EXPIRE 实现滑动窗口计数器。以 endpoint_hash:ip 为 key 统计每秒请求量，超过阈值（可配置，默认 100/秒/IP）时返回 429。

错误处理

Redis 错误处理策略： 1. 连接异常：Redis 连接超时或断开时，各服务使用连接池自动重连。连接池配置 max_idle=10、max_active=50、dial_timeout=3s。连接失败时服务降级为直读 MySQL（Cache-Aside 模式），保证核心部署流程不受影响。降级期间记录 WARN 日志。 2. 读写超时：所有的 Redis 命令设置 read_timeout=3s、write_timeout=3s。超时发生时记录错误日志并降级至 MySQL 读取，不阻塞主业务流程。 3. 主从切换：Redis Sentinel 或 Cluster 模式下发生主从切换时，连接池中的旧主连接失效。客户端驱动自动发现新主节点，期间短暂不可用（通常 < 1s），应用程序层重试 1 次即可恢复。 4. 内存淘汰策略：Redis 配置 maxmemory 和 allkeys-lru 淘汰策略。缓存键需要正确设置 TTL，确保热点数据在内存中、冷数据被自动淘汰。deployment_log_buffer 使用 LTRIM 限制单个 key 的 List 长度，防止单个部署日志过多耗尽内存。 5. 键冲突处理：统一命名空间前缀（deploy:/ws:/config:/ratelimit:）隔离不同业务模块的键，避免命名冲突。连接不同 Redis 数据库（db0=业务缓存/db1=会话/db2=限流）进一步隔离。 6. 数据丢失补救：Redis 纯内存非持久化模式（不开启 RDB/AOF，接受缓存丢失），缓存丢失时通过 Cache-Aside 模式的回源机制从 MySQL 重新加载数据。日志数据在部署终态后由 SSH 执行代理写入 MySQL 持久化，Redis 中的日志缓冲区视为临时副本，丢失不影响最终一致性。 7. 并发竞争：部署状态更新可能多端并发写入（SSH 执行代理回写 + 部署编排服务更新）。使用 Redis 的 GETSET/INCR 原子操作处理计数器类场景；非原子操作的字段更新在应用层获取锁（SET NX 实现分布式锁，lock_key=deploy:lock:{deployment_id}，TTL=10s）或接受最终一致性（部署状态最终以 MySQL 为准）。 8. Pub/Sub 可靠性：Redis Pub/Sub 为即发即忘模式，订阅者离线时消息丢失。因此关键状态变更使用双写策略：同时发布到 Pub/Sub（实时推送）和写入 deployment_status_cache（前端轮询兜底）。WebSocket 推送模块启动时重新连接订阅，确保不会错过后续消息。 9. 限流精度：滑动窗口基于每秒粒度，INCR + EXPIRE 1 实现。对精度要求不高的场景可容忍 ±1 秒的窗口漂移。需要更高精度时改用 Redis Sorted Set（ZADD + ZREMRANGEBYSCORE）实现毫秒级滑动窗口。 10. 连接池耗尽：Redis 连接池全部被占用时新请求等待 pool_timeout=1s，超过后降级至 MySQL，返回降级响应的同时记录告警日志，通知运维检查 Redis 负载或扩容。
