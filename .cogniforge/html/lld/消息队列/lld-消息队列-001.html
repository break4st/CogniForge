概述

模块: 消息队列

消息队列是基于 AMQP 协议的异步消息中间件，位于系统数据层，核心作用是解耦部署编排服务与SSH执行代理之间的同步依赖。部署编排服务将部署任务以消息形式投递至 deployment.tasks 队列，SSH执行代理异步消费执行；SSH执行代理在执行过程中将日志行与状态变更以消息形式回写至 deployment.logs 队列，部署编排服务异步消费处理后推送 WebSocket 及更新数据库。采用 Direct Exchange 路由模型，消息持久化确保 Broker 重启不丢消息。每条队列绑定独立死信交换机（DLX），消费失败重试3次后自动路由至死信队列，防止消息堆积阻塞正常消费。配合消费者确认机制（manual ack）实现 Exactly-Once 投递语义（结合业务幂等去重），prefetch_count=1 保证公平分发。所有队列设置消息 TTL（24h），超时未消费的消息自动过期进入死信队列。

接口定义 (6)

PublishToTasks

AMQP::channel.basicPublish — exchange=amq.direct, routingKey=deployment.tasks

部署任务消息投递接口。部署编排服务 TriggerDeployment 流程中在部署记录创建成功后调用此接口，将 DeploymentTaskMessage 投递至 deployment.tasks 交换机。投递时设置 deliveryMode=2（持久化）和 expiration=86400000（24h TTL）。投递失败时业务层回滚部署记录并返回 502。该接口要求必须确认消息已到达交换机（Publisher Confirm 模式），防止 Broker 接收前丢失。

参数类型描述
exchangestring目标交换机，固定值 amq.direct
routingKeystring路由键，固定值 deployment.tasks
bodyJSON stringDeploymentTaskMessage 的 JSON 序列化字符串
deliveryModeinteger消息持久化标识，固定值 2
expirationstring消息 TTL（毫秒），固定值 '86400000'（24h）
headersobject消息头，包含 content_type=application/json 及自定义 trace_id 用于链路追踪

PublishToLogs

AMQP::channel.basicPublish — exchange=amq.direct, routingKey=deployment.logs

日志回写消息投递接口。SSH执行代理在部署执行过程中调用此接口，将 DeploymentLogMessage 投递至 deployment.logs 交换机。日志消息重要性低于任务消息，不要求 Publisher Confirm 严格确认（Fire-and-Forget 模式），代理内部重试3次仍失败后降级至本地日志，不阻塞部署执行。但 status_change 类型的消息建议启用 Publisher Confirm，确保部署状态变更可靠传递。

参数类型描述
exchangestring目标交换机，固定值 amq.direct
routingKeystring路由键，固定值 deployment.logs
bodyJSON stringDeploymentLogMessage 的 JSON 序列化字符串
deliveryModeinteger消息持久化标识，固定值 2
expirationstring消息 TTL（毫秒），固定值 '3600000'（1h）
headersobject消息头，包含 content_type=application/json

ConsumeDeploymentTasks

AMQP::channel.basicConsume — queue=deployment.tasks, autoAck=false

部署任务消费接口。SSH执行代理通过此接口从 deployment.tasks 队列拉取任务消息。采用手动确认模式（autoAck=false），消息处理成功（脚本启动完成）后调用 basicAck 告知 Broker 删除消息；处理失败时调用 basicNack(requeue=true)，Broker 将消息重新入队投递给其他消费者。同一消息最多重试3次，重试次数记录在消息头 x-death 中，超过3次后调用 basicNack(requeue=false) 将消息投递至死信队列。

参数类型描述
queuestring队列名，固定值 deployment.tasks
autoAckboolean是否自动确认，固定值 false（手动确认）
prefetchCountintegerQoS 预取计数，固定值 1（每次只取一条，保证公平分发）
consumerTagstring消费者标签，格式 ssh-agent-{hostname}-{pid}，用于运维识别消费者来源
callbackfunction消息处理回调函数，接收 deliveryTag/envelope/body/properties，内部实现幂等去重、反序列化、SSH执行、ack/nack 决策

ConsumeDeploymentLogs

AMQP::channel.basicConsume — queue=deployment.logs, autoAck=false

日志回写消息消费接口。部署编排服务通过此接口从 deployment.logs 队列拉取 SSH执行代理 回写的日志消息。采用手动确认（autoAck=false）和批量确认模式配合 prefetch_count=100 提升吞吐。消费处理逻辑：反序列化为 DeploymentLogMessage → type=log 写入 deployment_logs 表 + WebSocket 推送 → type=status_change 更新 deployments 表 + WebSocket 推送。处理成功后 basicAck 单条确认；WARN 级别异常使用 basicNack(requeue=true) 重试；ERROR 级别异常使用 basicNack(requeue=false) 投递死信。

参数类型描述
queuestring队列名，固定值 deployment.logs
autoAckboolean是否自动确认，固定值 false
prefetchCountintegerQoS 预取计数，固定值 100（批量消费提升吞吐）
consumerTagstring消费者标签，格式 orchestrator-{hostname}-{pid}
callbackfunction消息处理回调函数

AcknowledgeMessage

AMQP::channel.basicAck / basicNack

消息确认与拒绝接口。消费者处理完消息后需显式调用确认或拒绝接口告知 Broker 处理结果。basicAck 通知 Broker 消息已成功处理可删除；basicNack 通知 Broker 需重新入队或投递死信。确认操作必须在消费通道中执行，Broker 通过 deliveryTag 精确定位消息。

参数类型描述
actionstring确认动作，枚举值：ack / nack_requeue / nack_deadletter
deliveryTaginteger投递标签，从消息投递回调中获取，唯一标识本次投递
multipleboolean是否批量确认，true 表示确认 deliveryTag 及之前所有未确认消息（仅用于 basicAck）
requeuebooleannack 时是否重新入队：nack_requeue=true（重试）、nack_deadletter=false（死信）

ConnectionManager

AMQP::connect / close / recovery

连接生命周期管理接口。消息队列客户端与 Broker 之间通过 TCP 长连接通信，连接管理器负责连接的创建、心跳保活、自动重连与优雅关闭。所有生产者和消费者共享连接管理器实例，通过 Channel 复用连接。Broker 重启或网络闪断时自动重连，重连期间生产者消息排队缓冲至本地内存（最多 1000 条），消费者连接恢复后自动恢复队列监听。

参数类型描述
connectfunction建立与 Broker 的 TCP 连接，参数从 ConnectionPoolConfig 读取，返回 Connection 对象
createChannelfunction在已有连接上创建 AMQP 通道（Channel），每个 Channel 独立序号。生产者和消费者使用不同 Channel 隔离
closeChannelfunction关闭指定 Channel，释放资源。服务关闭时逐个关闭所有 Channel
closeConnectionfunction关闭与 Broker 的 TCP 连接，优雅关闭时先停止消费者再关闭连接
recoveryCallbackfunctionBroker 断线重连成功后的恢复回调，自动重新声明交换机/队列/绑定并恢复消费者监听

错误处理

消息队列提供分层错误处理策略，覆盖生产者投递异常、消费者处理异常、连接层异常三类场景： 1. 生产者投递失败：PublishToTasks/PublishToLogs 投递时 Broker 连接不可用或写入超时（3s），客户端捕获 AMQPException 后重试3次（间隔500ms），仍失败则回滚业务操作（部署编排服务将部署记录标记为 failure 并返回502 SSH_KEY_DECRYPT_FAIL），或降级记录本地日志（SSH执行代理回写日志时）。启用 Publisher Confirm 模式确保投递确认，Broker 返回 basicAck 前客户端阻塞等待。 2. 消费者消息反序列化失败：ConsumeDeploymentTasks 接收的消息 JSON 格式损坏或字段缺失，调用 basicNack(requeue=false) 直接投递死信队列，记录错误日志并输出 messageId 用于排查，错误码 MSG_DESERIALIZE_FAILED。 3. 消费者处理超时：部署编排服务消费 deployment.logs 消息时写入 MySQL 超时（>5s），调用 basicNack(requeue=true) 重新入队。重试累计3次后 basicNack(requeue=false) 投递死信，错误码 MSG_CONSUME_TIMEOUT。 4. 消费者业务异常：SSH执行代理 SSH 连接失败阶段触发 nack，deployment.tasks 消息重新入队。需注意 Broker 默认 immediate requeue 会导致死循环，因此客户端在 nack 前检查 x-death header 中的重试次数：重试 <3 次时 basicNack(requeue=true)，≥3 次时 basicNack(requeue=false) 投递死信。 5. 连接断线自动重连：Broker 宕机或网络分区导致连接断开时，客户端自动重连（心跳超时 60s 触发检测）。重连间隔 5s，最多重试 10 次。重连期间生产者使用本地内存缓冲队列（容量 1000 条队列缓冲，日志消息最多缓冲 5000 条），消费者监听自动恢复（队列和交换机声明在内置 onReconnect 回调中重做）。第 11 次连接后仍失败则触发服务级降级：部署编排服务返回 503 并提示用户稍后重试，SSH执行代理停止消费并等待人工恢复。 6. 死信队列堆积告警：deployment.tasks.dlx 和 deployment.logs.dlx 队列消息数超过告警阈值（任务死信 >10 条、日志死信 >100 条）时触发告警通知运维人员。告警通过独立监控进程定时（每 5 分钟）调用 Management API（RabbitMQ HTTP API）查询队列深度实现。 7. 消息重复投递：消费者进程在处理消息过程中崩溃（已处理完成但未 ack），Broker 检测到连接断开后将未 ack 消息重新入队投递给其他消费者。消费者需通过 task_id（DeploymentTaskMessage）幂等去重：SSH执行代理在消费前检查 task_id 是否已在本地已处理集合中（内存 Set + 定时清理），存在则 basicAck 并跳过执行。 8. 无序消费风险：deployment.logs 同一 deployment_id 的日志消息可能被多个消费者实例并行消费导致顺序错乱。解决方案：在消费者端按 deployment_id 分组，同一 deployment_id 的消息由同一 goroutine/线程串行处理，或使用 Sender Ack 模式在写入 MySQL 时通过 sequence 字段检测乱序并重排。 9. 队列积压：deployment.tasks 队列堆积（部署请求 > 消费能力）时水位升高。监控队列深度，超过 500 条时触发告警。系统通过 SSH执行代理 水平扩展（增加消费者实例数量）提升消费速度实现削峰填谷。deployment.logs 堆积不阻塞关键业务，日志写入 MySQL 可能延迟但不会丢失。 10. 优雅关闭：收到 SIGTERM 信号时，生产者停止投递新消息并刷新本地缓冲队列中剩余消息至 Broker；消费者调用 channel.basicCancel 取消监听，等待正在处理的消息完成 ack（最多 30s），30s 后未完成的强制 nack 并关闭连接。确保服务重启期间消息不丢失不重复处理。
