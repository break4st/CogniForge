概述

部署编排服务
⚙️ 业务服务
部署任务的核心编排器，负责版本文件夹创建、文件上传、脚本生成和执行。接收部署请求并创建部署任务，通过SSH在远程创建版本文件夹，上传可执行文件到远程服务器，生成并执行启动脚本，收集部署日志和状态反馈，发布部署状态事件到消息队列。
依赖: SSH连接池密钥存储服务消息队列PostgreSQL数据库文件存储
GoGinPostgreSQL 15RabbitMQgolang.org/x/crypto/sshgorilla/websocket

业务规则

不变量
  • !同一项目+同一环境不允许同时存在两个 running 状态的部署任务
  • !部署版本号在同一项目内必须唯一，不允许重复部署相同版本
  • !部署步骤必须严格按照「创建版本目录→上传文件→生成脚本→执行启动」顺序执行，不可跳跃或并行
  • !部署状态流转必须遵守状态机定义，不可跳过 running 直接从 pending 到 success
  • !每一个 deployment_step 必须关联一个有效的 deployment_id
  • !SSH连接凭证必须通过密钥存储服务获取，本服务不得直接存储明文认证信息
状态机
🎯 DeploymentTask
pendingrunningsuccessfailed
→DeploymentService.ExecuteDeploymentTask 开始执行第一个步骤by 系统（MQ消费者worker）
→所有部署步骤执行完毕且退出码均为 0by 系统（步骤执行器）
→任意步骤执行返回非零退出码或抛出未恢复异常by 系统（步骤执行器）
→预校验失败（环境不可达/密钥无效）或用户主动取消部署by 系统/用户
🚫 success 和 failed 为吸收态（absorbing state），一旦到达不可转换到任何其他状态🚫 不可从 success 回退到 running 或 pending🚫 不可从 failed 恢复到 running，需要重新创建部署任务
⚡ 通过数据库层唯一约束+状态检查确保并发安全：CreateDeployment 方法中先查询是否存在 running 状态的部署（SELECT ... FOR UPDATE），存在则返回 409 冲突；状态更新使用乐观锁 WHERE status=当前状态，影响行数为 0 时说明并发冲突需重试
跨服务规则
部署任务创建后必须立即发布到 MQ exchange.deployment.task，确保消息不丢失（使用事务确认模式），MQ 发布失败需回滚数据库写入
SSH 执行前必须先从密钥存储服务 (GET /api/v1/keys/{key_id}) 获取解密后的连接凭证，获取失败则步骤标记 failed
每次状态变更（pending→running/running→success/running→failed）必须同步完成两件事：写入 deployments 表 + 发布到 MQ exchange.deployment.status，使用最终一致性保证（先写 DB 再发 MQ，MQ 失败则本地日志兜底）
每一条部署日志必须写入 deployment_logs 表并发布到 MQ exchange.deployment.log，日志服务通过异步方式消费和分发，写 DB 失败不影响部署主流程（日志可降级，使用缓冲队列暂存）
文件上传到远程服务器前如需从文件存储模块获取文件内容，调用文件存储内部接口 DownloadFile 获取文件流，上传完成后记录文件路径到 deployments.file_path
WebSocket 日志推送服务通过消费 MQ queue.deployment.log 队列获取日志事件，MQ 断开时 WebSocket 客户端应自动重连并拉取最近缺失的日志作为补偿

错误处理

处理策略

采用统一JSON错误响应格式。参数校验错误返回4xx，业务冲突返回409，服务依赖异常返回502或503，内部错误返回500。所有错误记录审计日志，可重试错误（如MQ临时失败）由后台worker自动重试。
