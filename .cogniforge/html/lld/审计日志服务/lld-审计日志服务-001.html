概述

审计日志服务
⚙️ 业务服务
记录系统所有关键操作的审计日志，确保操作可追溯。负责接收各微服务的审计事件、持久化存储审计记录、支持审计日志的多维度查询与文件导出。作为系统可追溯性保障的核心模块，所有关键业务操作（部署、密钥管理、项目变更、环境配置等）均须通过此服务记录，形成完整操作审计链。
依赖: PostgreSQL数据库
PythonFastAPIPostgreSQL 15

业务规则

不变量
  • !审计日志一旦写入即不可修改、不可删除，属于仅追加（append-only）数据
  • !每条审计日志必须包含操作人身份信息（operator_id + operator_name）和操作发生时间（timestamp）
  • !审计日志的 timestamp 由调用方传入，表示实际业务操作的发生时间，区别于日志在服务端的写入时间
  • !action 字段必须遵循 {resource_type}.{operation} 的命名规范，如 deployment.create、project.update、key.revoke
  • !查询审计日志的时间范围跨度不得超过 90 天，防止全表扫描导致的性能问题
  • !resource_type 取值必须为预定义的枚举值：project/environment/deployment/key 之一
状态机
🎯 audit_logs 表分区生命周期
在线归档已清理
→数据超过 12 个月，定时任务触发分区迁移by 定时调度
→数据超过合规保留期（如 3 年），定时清理任务执行by 定时调度
🚫 在线 → 归档 为单向迁移，归档数据不可回迁至在线分区🚫 归档 → 已清理 为不可逆删除操作，执行前需确认合规保留期已届满
⚡ 分区切换操作在业务低峰期执行，使用排它锁保证同一时间只有一个迁移任务运行。查询语句通过 timestamp 字段自动路由到对应分区，迁移过程对业务查询透明
跨服务规则
项目管理服务在创建/更新/删除项目操作完成后，必须调用 POST /api/internal/audit-logs 记录审计日志，传入 resource_type=project
环境管理服务在创建/更新/删除环境配置操作后，必须调用 POST /api/internal/audit-logs 记录审计日志，传入 resource_type=environment
部署执行服务在部署任务状态变更时（pending→running→success/failed），必须在每个状态变更节点调用 POST /api/internal/audit-logs 记录部署生命周期的完整轨迹，传入 resource_type=deployment
密钥管理服务在上传/吊销/轮换 SSH 密钥操作后，必须调用 POST /api/internal/audit-logs 记录密钥操作，传入 resource_type=key
各微服务调用审计日志接口时，ip_address 必须从请求的 X-Forwarded-For 或真实客户端 IP 中获取（而非服务内部 IP），确保操作溯源准确性
审计日志 detail 字段应包含足以还原操作上下文的摘要信息（如变更前后的关键字段），但不得包含敏感信息（如密码、密钥原文、令牌令牌）
调用方应在业务操作成功或失败后同步调用审计日志接口，确保操作记录不丢失。若审计日志服务暂时不可用，调用方应采用异步重试策略（最多重试 3 次，间隔 1s/3s/5s），不可阻断主业务流程

错误处理

处理策略

审计日志服务采用统一异常处理机制，所有控制器层异常通过全局异常处理器捕获并转换为结构化 JSON 响应。参数校验异常（ValidationException）在控制器层通过 Pydantic 模型校验自动触发，业务约束异常（时间范围超限、导出上限）在服务层显式抛出，数据库异常（连接超时、写入失败）在仓储层捕获并转换为友好错误信息。审计日志仅追加不修改，不存在业务冲突场景。
