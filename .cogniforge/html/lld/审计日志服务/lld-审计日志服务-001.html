概述

审计日志服务
⚙️ 业务服务
记录系统中所有关键操作的审计日志，确保操作可追溯。接收各业务服务（项目管理服务、环境管理服务、部署引擎服务、密钥管理服务）的操作记录请求，将审计信息持久化存储并支持条件查询
GoGinGo 1.22+PostgreSQL 15
🗄️

服务接口 (1)

🔧 AuditLogService 3 方法
Record
(ctx context.Context, req RecordAuditLogRequest) -> (RecordAuditLogResponse, error)
将一条审计日志记录持久化到数据库，接收业务服务传递的操作信息
前置条件
req.action 非空且长度不超过 128；req.actor 非空且长度不超过 64；req.resource_type 非空且长度不超过 64；req.detail 如提供须为合法 JSON
后置条件
审计日志写入 audit_logs 表，id 由数据库自增生成，created_at 设为 req.timestamp（系统自动补当前时间），返回的 log_id 对应新记录主键且 recorded=true
ErrInvalidArgument→ 400action、actor 或 resource_type 为空或超长ErrInternal→ 500数据库 INSERT 失败、连接异常或 JSON 序列化失败
Query
(ctx context.Context, req QueryAuditLogRequest) -> (AuditLogPage, error)
按多条件组合筛选查询审计日志，支持精确匹配和时间范围查询
前置条件
req.page 穿透设默认值 1 后必须 >= 1；req.page_size 默认 20；req.start_time 和 req.end_time 如同时提供须 start_time <= end_time
后置条件
返回符合所有筛选条件的审计日志分页列表，按 created_at 降序排序；filter 条件之间为 AND 关系；无匹配记录时返回 items=[]、total=0、page=req.page、page_size=req.page_size
ErrInvalidArgument→ 400page < 1 或 page_size < 1 或 page_size > 100 或 start_time > end_timeErrInternal→ 500数据库 SELECT 查询失败或连接异常
GetByID
(ctx context.Context, id int64) -> (AuditLog, error)
按主键 ID 获取单条审计日志的完整信息
前置条件
id 必须为正整数
后置条件
返回与 id 匹配的完整 AuditLog 实体；不存在时返回 ErrAuditLogNotFound
ErrAuditLogNotFound→ 404指定 id 的审计日志在数据库中不存在ErrInvalidArgument→ 400id 为 0 或负数ErrInternal→ 500数据库查询失败
数据访问依赖
Insert(auditLog *AuditLog) -> error
FindByFilters(req QueryAuditLogRequest) -> ([]AuditLog, int, error)
FindByID(id int64) -> (*AuditLog, error)

业务规则

不变量
  • !审计日志记录一旦写入不可修改、不可删除（append-only），由服务层业务逻辑和数据库用户权限共同保证，审计日志服务连接数据库仅具备 SELECT 和 INSERT 权限
  • !每条审计日志必须包含非空的 action、actor 和 resource_type 字段
  • !action 命名遵循 module.verb 规范，如 project.create、deploy.start
  • !resource_type 使用单数小写英文，如 project、environment、key、deploy
  • !审计日志时间线统一使用 UTC 时区，created_at 和查询参数均以 ISO8601 格式传递
状态机
🎯 AuditLog
recorded
🚫 审计日志一旦写入即为终态 recorded，不允许任何状态变更（无 update、无 delete）🚫 历史记录永久保留，不存在软删除或物理删除场景
⚡ 审计日志为 append-only 写入，不存在同记录并发冲突场景。并发 INSERT 通过数据库 READ COMMITTED 隔离级别保证正确性，无需悲观锁或乐观锁
跨服务规则
各业务服务通过 POST /api/v1/audit-logs 接口记录审计日志，调用失败不应阻塞业务主流程（调用方应以异步方式调用，超时或错误时仅记录日志）
审计日志服务无其他业务服务依赖，独立提供存储和查询能力，不参与业务事务边界
审计日志的 timestamp 由调用方传入以保留操作发生的原始时间点，与数据库 created_at 字段对应；支持异步写入场景下时间戳精确性
审计日志查询接口供 Web 控制台通过 API 网关调用，提供操作历史追溯和审计能力
审计日志服务数据库仅分配 SELECT 和 INSERT 权限，从数据库层杜绝 UPDATE 和 DELETE 操作的可能性

错误处理

处理策略

采用统一 HTTP 状态码 + JSON 错误体格式返回错误信息。参数校验失败返回 400 并指明具体字段名，资源不存在返回 404，服务器内部错误返回 500。审计日志为 append-only 写入，不存在更新冲突场景，无需处理乐观锁或并发写入异常
