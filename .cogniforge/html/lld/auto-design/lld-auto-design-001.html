概述

auto-design
⚙️ 业务服务
根据已批准的PRD和SAD文档，自动生成模块详细方案，涵盖数据模型、接口定义和错误处理策略。该服务是一个无状态的智能化设计自动化引擎，通过内置规则和模板将需求转化为符合 CogniForge 规范的 LLD。
Python 3.11FastAPI

服务接口 (1)

🔧 DesignService 1 方法
generateDesign
generateDesign(request: DesignGenerationRequest) -> DesignGenerationResponse
核心方法，接收设计请求，驱动规则引擎和模板生成最终的详细设计文档。
前置条件
request 对象非空；prdDocument 和 sadDocument 能被成功解析；prdDocument.meta.status 的值为 "approved"。
后置条件
返回的响应中包含一个完整的、符合 CogniForge LLD JSON Schema 的 lld 字段。
DocumentValidationException→ 400PRD 结构无效、SAD 结构无效或 PRD 状态不为 approved。DesignGenerationConflictException→ 409系统内已存在一个针对相同 prd.doc_id 的 PROCESSING 状态任务。DesignEngineException→ 500规则推导失败、模板渲染出错等内部处理异常。
📐

业务规则

不变量
  • !输入的 PRD 文档的 meta.status 字段值必须始终为 "approved"。
  • !生成的 LLD 文档的 meta.author 字段值固定为 "design_agent"。
  • !生成的设计方案中，所有数据模型引用（ownership 为 derived）的 source.doc_id 必须能与系统内的现有 LLD 文档匹配。
状态机
🎯 DesignTask
PENDINGPROCESSINGCOMPLETEDFAILED
→开始处理by Design Worker
→生成成功by Design Engine
→生成异常/规范不明确by Design Engine
🚫 一旦进入 COMPLETED 或 FAILED 状态，任务即终止，不可逆转至 PENDING 或 PROCESSING。
⚡ 基于 prd.doc_id 的分布式锁控制，确保同一文档仅有一个任务处于 PROCESSING 状态。
跨服务规则
当为新模块设计方案时，若需引用数据库表，必须在 data_models 中使用 ownership: "derived"，并准确指向 Primary Database 模块 LLD 中的表定义，如 source: { "doc_id": "lld-Primary Database-001", "model_name": "users" }。

⚠️

错误处理

处理策略

采用分层错误处理。接口层负责参数校验和格式错误(400)，服务层负责业务逻辑冲突(409)和内部异常(500)。所有错误响应统一使用标准格式。

统一错误响应体
字段类型
codeinteger
errorstring
detailstring
4xx
校验失败
当输入的 PRD/SAD 结构不符合要求，或其 status 不为 'approved' 时触发。处理方式：直接返回错误详情，指明具体无效字段及原因。
4xx
业务冲突
当存在并发任务正在为同一 prd.doc_id 生成设计时触发。处理方式：返回 409 冲突错误。
5xx
服务端错误
当 AI 推理失败、模板引擎异常或内存溢出等内部错误时触发。处理方式：记录详细错误日志，并返回通用内部错误信息。
