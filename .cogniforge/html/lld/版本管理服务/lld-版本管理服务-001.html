概述

版本管理服务
⚙️ 业务服务
管理部署版本记录，支持版本回滚。该服务为部署编排服务的下游依赖，负责版本号自动生成、版本历史记录查询、版本状态管理（active/inactive/rolled_back）、版本间差异对比。部署编排服务在每次成功部署后调用本服务创建版本记录，在回滚操作完成后调用本服务更新版本状态。Web管理控制台通过查询接口获取版本历史列表和当前运行版本。
依赖: 部署编排服务项目管理服务环境管理服务
GoGinPostgreSQL 15+Redis 7+

服务接口 (1)

🔧 VersionService 6 方法
CreateVersion
(ctx context.Context, req *CreateVersionRequest) (*DeploymentVersion, error)
创建版本记录。自动生成版本号，将前一个活跃版本标记为 inactive，新增记录初始状态为 active。使用数据库事务保证原子性。
前置条件
req 中 project_id/environment_id/task_id/deployed_by 对应的记录必须存在于各自表中；task_id 不得已关联过其他版本记录；当前无活跃版本或活跃版本的 task 未处于 running 状态
后置条件
数据库中插入一条新版本记录，status=active，version 按格式自动生成；之前 active 的版本（若有）status 变更为 inactive；版本变更写入审计日志
ErrDuplicateTaskID→ 409task_id 已存在于 deployment_versions 表ErrResourceNotFound→ 404project_id/environment_id/deployed_by 引用不存在ErrDatabase→ 503数据库写入失败或事务提交失败
QueryHistory
(ctx context.Context, params *VersionQueryParams) (*PaginatedResult, error)
查询版本历史列表。支持按状态筛选、分页和排序。优先从 Redis 缓存读取（缓存命中直接返回），缓存未命中则查询 PostgreSQL 并回填缓存。

params.project_id 和 params.environment_id 为有效 UUID；page >= 1；page_size 在 [1, 100] 范围内
后置条件

GetCurrentActive
(ctx context.Context, projectID, environmentID uuid.UUID) (*VersionSummary, error)
获取当前活跃版本。查询指定项目和环境下 status=active 的最新一条记录。结果缓存到 Redis（TTL=120s），版本状态变更时主动失效。
前置条件
projectID 和 environmentID 为有效 UUID

Rollback
(ctx context.Context, targetVersionID uuid.UUID, req *RollbackRequest) (*DeploymentVersion, error)
版本回滚。将目标版本（回滚目标）恢复为 active，被回滚版本标记为 rolled_back。使用数据库事务保证两条记录状态变更的原子性。
前置条件
targetVersionID 与 req.rolled_back_from_version_id 不同；targetVersionID 对应记录存在且 status=inactive；rolled_back_from_version_id 对应记录存在且 status=active
后置条件
targetVersionID 对应记录 status 变更为 active，rolled_back_from_version_id 对应记录 status 变更为 rolled_back（并写入 rolled_back_at 和 rolled_back_to）；两个变更在同一数据库事务中完成；相关缓存（active 版本和列表缓存）全部失效
ErrVersionNotFound→ 404targetVersionID 或 rolled_back_from_version_id 不存在ErrInvalidRollback→ 400targetVersionID == rolled_back_from_version_id（不能回滚到自身）ErrVersionNotRollbackable→ 409目标版本 status!=inactive（rolled_back 终态不可回退）ErrActiveVersionMismatch→ 409rolled_back_from_version_id 的 status 不是 active（不存在冲突的活跃版本）ErrDatabase→ 503事务提交失败或并发冲突

业务规则

不变量
  • !任意 (project_id, environment_id) 组合下，最多只能有一条版本记录的 status = active
  • !版本号格式必须为 v{YYYYMMDD}.{HHMMSS}.{3位序列}，同一项目和环境下的版本号全局递增不重复
  • !task_id 在 deployment_versions 表中全局唯一，一个部署任务只能关联一个版本记录
  • !rolled_back 状态的版本记录不可再变更为任何其他状态（终态不可逆）
  • !回滚操作必须指定不同的两个版本：被回滚版本（当前 active）和目标版本（回滚目标，当前 inactive）
  • !版本记录的 created_at 一经写入不可修改
状态机
🎯 DeploymentVersion
activeinactiverolled_back
→成功部署（CreateVersion 调用）by 部署编排服务
→新的部署版本创建，自动将前一个 active 降级为 inactiveby 版本管理服务（内部自动触发）
→回滚操作（Rollback 调用）：该版本被从活跃状态回滚by 部署编排服务
→回滚操作（Rollback 调用）：该版本被恢复为活跃版本by 部署编排服务
🚫 rolled_back 状态为终态：处于 rolled_back 的版本不可再变更为 active 或 inactive🚫 回滚不可撤销：一旦执行回滚操作，被回滚版本（active → rolled_back）不可再恢复为 active🚫 相同内容和配置的重新部署应以新版本号创建，而非恢复旧版本
⚡ 回滚操作使用数据库行级锁（SELECT ... FOR UPDATE）锁定涉及的两条版本记录；乐观锁通过 WHERE status=预期状态 保证条件不冲突；若两条记录被并发回滚操作锁定，第二个操作等待行锁释放后检测到状态已变更，返回 ErrActiveVersionMismatch
跨服务规则
版本创建由部署编排服务在成功部署后调用：部署编排服务保证文件传输和健康检查完成后才调用 CreateVersion 接口
版本回滚由部署编排服务协调：编排服务负责远程服务器上的目录切换和启动脚本执行，版本管理服务仅负责状态记录
版本查询接口返回的 deployed_by_name 由版本管理服务查询用户服务或通过 JOIN users 表获取
项目删除操作（项目管理服务）必须先检查关联的版本记录并阻止删除：项目管理服务在删除 project 前应调用版本管理服务确认无关联版本
环境删除操作（环境管理服务）应先确认环境无活跃版本：环境管理服务可调用 GetCurrentActive 接口检查
审计日志记录由审计日志服务统一负责：版本管理服务在关键操作（版本创建、回滚）后通过 MQ 发送审计事件，由审计日志服务消费写入 audit_logs 表

错误处理

处理策略

所有版本操作统一使用事务保证数据一致性。版本回滚涉及两个版本记录的状态变更，必须在一个数据库事务中完成（全成功或全回滚）。参数校验失败返回 400，记录不存在返回 404，业务约束冲突（唯一性、状态非法）返回 409。内部服务调用超时默认 10s，超时返回 504。数据库连接异常时最多重试 2 次（指数退避），重试仍失败则返回 503。

统一错误响应体
字段类型
codeinteger（HTTP状态码）
errorstring（错误分类标识，如 VERSION_NOT_FOUND）
detailstring（详细错误描述，包含冲突的字段和值）
400
参数校验错误
请求参数格式错误或必填字段缺失。触发条件：project_id 为空、page_size 超过 100、版本号格式非法。处理方式：返回 400，detail 字段注明具体哪个参数校验失败。
404
资源不存在
请求的版本记录、关联的项目或环境不存在。触发条件：查询不存在的版本 ID、项目已删除。处理方式：返回 404，detail 注明资源类型和标识。
409
业务约束冲突
操作违反业务规则。触发条件：重复的 task_id、回滚目标版本已处于 rolled_back 终态、回滚到自身。处理方式：返回 409，detail 说明具体冲突规则。
503
数据库不可用
PostgreSQL 连接失败或查询超时。触发条件：数据库重启、网络分区、连接池耗尽。处理方式：自动重试 2 次（100ms/500ms 指数退避），全部失败返回 503，引导用户稍后重试。
504
上游服务超时
调用项目管理服务或环境管理服务的内部请求超时。触发条件：版本创建时验证项目/环境存在性超时（>10s）。处理方式：返回 504，提示用户检查关联服务状态。
