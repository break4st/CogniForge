概述

Deployment Orchestrator
⚙️ 业务服务
部署流程的编排引擎，负责部署任务接收、状态管理和进度发布。接收来自 API Gateway 的 REST 部署请求，创建部署记录并发布部署任务消息到 RabbitMQ。通过消费 SSH Execution Service 的进度消息更新部署状态，实时状态通过 Redis 缓存加速查询，最终结果持久化到 Primary Database。关键操作同步记录审计日志至 Audit Service。提供部署历史查询能力。
依赖: API GatewayPrimary DatabaseRedisRabbitMQSSH Execution ServiceAudit Service
Python 3.11+FastAPIasyncio + uvicornPostgreSQL 15Redis 7RabbitMQ 3.12Docker + Docker Compose

后置条件

业务规则

不变量
  • !同一项目+同一环境同时最多只能有一个非终态（status IN pending/running）的部署记录，并发提交时返回 409
  • !部署进度百分比 progress_pct 必须始终在 0-100 范围内，单调递增不减少
  • !部署状态转换必须严格遵循状态机定义：pending → running → running/success/failed，不可跳转或回退
  • !部署记录创建时必须包含 project_id、environment_id、version、artifact_path、created_by，缺一不可
  • !部署日志按时间顺序追加，仅追加不覆盖，用于完整追溯执行过程
  • !progress_pct 达到 100 时 status 必须为 success（正常完成）或 failed（最后一步失败），不可仍为 running
  • !failed 状态的部署必须有 finished_at 时间戳和至少一条错误日志
状态机
🎯 Deployment
pendingrunningsuccessfailed
→SSH Execution Service 确认消费 MQ 消息并开始执行首步部署操作，第一条 DeployProgressMessage（status=running）到达by DeploymentOrchestratorService (via DeployProgressMessage consumer)
→SSH Execution Service 完成单个步骤并发布进度更新，progress_pct 增加、current_step 更新by DeploymentOrchestratorService (via DeployProgressMessage consumer)
→SSH Execution Service 完成所有部署步骤且退出码均为 0，发布 status=success 的终态进度消息by DeploymentOrchestratorService (via DeployProgressMessage consumer)
→任意部署步骤执行失败（命令退出码非零、SSH 连接中断、超时），发布 status=failed 的终态进度消息by DeploymentOrchestratorService (via DeployProgressMessage consumer)
🚫 部署进入 success 或 failed 终态后不可逆，不可转换为其他任何状态🚫 failed 状态的部署不会自动重试——需要用户重新提交部署请求创建新部署记录🚫 处于 pending 状态的部署如果超时（超过 30 分钟无进度更新）无自动状态变更机制，由运维人工排查 MQ 消费状态🚫 progress_pct 不会因应用重启或服务异常而递减或回滚
⚡ 同一 deployment 的进度消息消费通过 deployment_id 作 key 进行串行化处理，避免并发更新导致状态覆盖。同一项目不同环境的部署互不影响。不同项目的部署可并行处理。通过 RabbitMQ 单队列顺序消费保证同一部署的进度消息按发布顺序到达。
跨服务规则
部署任务通过 RabbitMQ 从本服务流向 SSH Execution Service：exchange deploy.tasks / routing_key deploy.execute。本服务负责组装 DeployTaskMessage（含 SSH 连接配置），消息持久化确保不丢失。不关心消费者具体处理细节
部署进度通过 RabbitMQ 从 SSH Execution Service 流向本服务：exchange deploy.progress / routing_key deploy.progress.update。本服务消费 DeployProgressMessage 更新状态。进度消息因业务原因消费失败时不重新入队，直接 ack，避免死信队列堆积
RabbitMQ 不可用时部署提交接口返回 503 拒绝服务，已创建的部署记录标记为 failed 并记录错误原因。已提交但尚未被消费的部署任务在 MQ 恢复后继续执行
部署关键事件（提交/完成/失败）通过 Audit Service 的 POST /internal/audit/log 接口同步记录审计日志。审计调用失败不影响主流程（fire-and-forget，本地记录 WARN 日志）
Redis 缓存用于加速状态轮询查询，是性能优化手段而非数据一致性的保证。Redis 不可用时所有状态查询回退到 Primary Database，系统功能不受影响仅查询延迟增加
本服务通过 Environment Management Service 的接口或数据库直接查询获取部署目标环境的 SSH 连接配置信息（host/port/username/key_id），组装到 DeployTaskMessage 中传递给 SSH Execution Service
SSH Execution Service 的 REST 接口（POST /internal/ssh/execute, POST /internal/ssh/upload）作为部署执行主路径（MQ 驱动）的备用路径预留，当前版本不直接调用

错误处理

处理策略

Deployment Orchestrator 对所有入参进行前置校验，校验失败返回 400。项目/环境/部署记录不存在返回 404。存在冲突部署（同一项目环境已有进行中部署）返回 409。RabbitMQ 连接失败返回 503。MQ 消息消费失败时记录错误日志并发送失败审计事件，消费 ack 异常时根据重试策略处理。所有未预期异常由全局异常处理器捕获返回 500。
